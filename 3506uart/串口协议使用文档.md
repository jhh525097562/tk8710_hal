# AG32 GPS PPS APP 串口协议说明

本文档对应 `app/src/pps_app.c` 当前 APP 固件。主机应使用本文列出的大写命令，参数以单个空格分隔。

## 1. 基本约定

- PC 向设备发送一条 ASCII 命令，以 `CR` 或 `LF` 结束。
- CPU 的每条返回/主动消息以换行结束；主机应以换行为一帧边界。
- `OK` 表示命令接受或查询成功；`ERR` 表示命令或参数错误；`EVENT` 表示 CPU 主动上报。
- 返回采用 `KEY=VALUE` 格式；未知字段应由主机忽略，以保持向前兼容。
- UTC 文本格式：`utc=YYYY-MM-DD HH:MM:SS.mmm`；UNIX 时间为 UTC 秒数。
- `0/1` 字段中，`0` 表示否/未使能，`1` 表示是/使能。

## 2. 命令清单

| 命令 | 用途 | 典型返回 |
| --- | --- | --- |
| `HELP` | 输出支持的命令列表，每行一条。 | `OK CMD:` 后跟命令清单 |
| `GET VERSION` | 查询 APP、BOOT、CPLD 的版本与构建信息。 | `OK APP_VER=... APP_BUILD=... BOOT_VER=... CPLD_VER=...` |
| `GET STATUS` | 查询单行运行摘要，供周期轮询使用。 | `OK STATUS ...` |
| `GET PERIOD` | 查询当前和待生效的 PPS_OUT 周期。 | `OK PERIOD=...` |
| `SET PERIOD <s> [target_utc]` | 设置周期，单位秒；可选指定目标 UTC 秒。 | `OK PERIOD=...` 或 `ERR BAD PERIOD/TARGET` |
| `GET WIDTH` / `SET WIDTH <ms>` | 查询或设置 PPS_OUT 脉宽，单位 ms。 | `OK WIDTH=...` 或 `ERR BAD WIDTH` |
| `OUT ON` / `OUT OFF` | 开启后重新对齐；关闭后清除待对齐和待周期变更状态。 | `OK OUT EN=1/0` |
| `GET OUT` | 查询 PPS_OUT、CPLD 状态和原始诊断计数。 | `OK OUT ...` |
| `GET PPS` | 查询 PPS_IN/CPLD 对齐与 CPU PPS 观测状态。 | `OK PPS ...` |
| `GET VERIFY` | 查询最近一次周期切换后的 CPLD 校验状态。 | `OK VERIFY ...` |
| `GET GPS` | 查询 GPS、RMC、UART 与 SNR 完整状态。 | `OK GPS ...` |
| `GET FIX` / `GET UTC` / `GET POS` / `GET SNR` | 查询定位、时间、位置和信噪比。 | `OK FIX/utc/POS/SNR ...` |

| `GET DEBUG` / `DEBUG ON/OFF` | 查询或控制额外的 GPS、SYNC、VERIFY 调试日志。 | `OK DEBUG=...` |
| `RESET GPS` | 触发 GPS 模块复位脉冲。 | `OK RESET GPS` |
| `ENTER BOOT` | 写入 BOOT 标志并进入升级流程。 | `OK ENTER BOOT` 或 `ERR ENTER BOOT WRITE` |

## 3. `GET STATUS`：推荐的常规轮询接口

```text
OK STATUS STATE=RUNNING PERIOD=1 OUT=1 WIDTH=100 PENDING=0 GPS=1 PPS=1 FIX=1 RMC=A ALIGN=1 HOLD=0 BAD=0 RESYNC=0 SATS=35 SNR=36 DEBUG=0 UTC=2026-08-31 05:37:18.000
```

| 字段                 | 含义                                                                                                                                                                 |
| ------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `STATE`            | `IDLE`：输出关闭；`WAIT_GPS`：输出已开但尚未具备 GPS 同步条件；`GPS_LOST`：GPS 已离线；`WAIT_TARGET`：已请求同步，正在计算/等待目标 UTC；`WAIT_PPS`：计划已写入，正在等目标 PPS 完成对齐；`RUNNING`：CPU 状态机正常运行；`ERROR`：未知状态。 |
| `PERIOD` / `WIDTH` | 当前 PPS_OUT 周期（秒）/高电平脉宽（毫秒），不是待生效值。                                                                                                                                 |
| `OUT`              | `1`：用户已执行 `OUT ON`，PPS_OUT 功能允许输出；`0`：用户已执行 `OUT OFF`。**`OUT=1` 不代表已经对齐。**                                                                                         |
| `PENDING`          | `1`：已接受 `SET PERIOD`，新周期尚未在目标 UTC 生效；`0`：没有待生效周期。**`PENDING=0` 不代表已经对齐。**                                                                                          |
| `GPS`              | `1`：GPS 在线；`0`：GPS 离线或 RMC 已超时。                                                                                                                                    |
| `PPS`              | `1`：CPLD 在健康窗口内检测到 PPS_IN；`0`：PPS_IN 丢失或尚未检测到。                                                                                                                     |
| `FIX`              | `1`：RMC、GGA、GSA 综合判定为有效定位；`0`：定位无效。                                                                                                                                |
| `RMC`              | `A`：最近 RMC 有效；`V`：最近 RMC 无效。                                                                                                                                       |
| `ALIGN`            | `1`：CPLD 已完成当前计划的对齐；`0`：尚未对齐或对齐已失效。                                                                                                                                |
| `HOLD`             | `1`：PPS_IN 丢失后 CPLD 正在守时；`0`：不在守时。                                                                                                                                 |
| `BAD`              | `1`：检测到 PPS_IN 周期异常；`0`：未检测到周期异常。                                                                                                                                  |
| `RESYNC`           | `1`：存在待处理的重同步请求，当前状态不能作为最终成功；`0`：没有待处理重同步。                                                                                                                         |
| `SATS` / `SNR`     | 在用卫星数 / 平均信噪比；数值越高通常表示接收条件更好，但不替代 `FIX`。                                                                                                                           |
| `DEBUG`            | `1`：会额外输出调试过程日志；`0`：只输出常规回复和重要事件。                                                                                                                                  |
| `UTC`              | 当前 GPS UTC；无有效 UTC 时为 `NA`。                                                                                                                                        |

主机通常每 1 至 10 秒调用一次 `GET STATUS`。出现异常或需要定位原因时，再发送对应详细 `GET` 命令。

**用户可开始工作的唯一明确事件：** `EVENT CPLD_ALIGNED RESULT=PASS READY=1 OUT=1 ALIGN=1 ...`。

#### PPS_OUT 当前工作状态判定

| 判定 | `GET STATUS` 组合 | 含义 |
| --- | --- | --- |
| 输出关闭 | `OUT=0` | 用户关闭了 PPS_OUT，不输出。 |
| 等待对齐 | `OUT=1 ALIGN=0`，通常 `STATE=WAIT_GPS/WAIT_TARGET/WAIT_PPS` | 已请求输出，但尚未完成当前计划对齐，不能认为输出稳定。 |
| 稳定、受 PPS 约束的输出 | `OUT=1 ALIGN=1 HOLD=0 BAD=0 RESYNC=0`，通常 `STATE=RUNNING` | **正常目标状态。** CPLD 已对齐，PPS_IN 当前健康，没有待处理重同步；可认为 PPS_OUT 正在稳定输出。若业务依赖 GPS，还应同时要求 `GPS=1 PPS=1 FIX=1 RMC=A`。 |
| 守时输出 | `OUT=1 ALIGN=1 HOLD=1` | PPS_OUT 仍继续输出，但 PPS_IN 已丢失，计数器冻结在最后校准值，偏差会随本地晶振累积；不能称为受 PPS 约束的稳定输出。 |
| 异常或等待恢复 | `BAD=1` 或 `RESYNC=1` | 检测到 PPS 周期异常或已请求重同步。即使 `ALIGN=1`，也应等待恢复事件或新的 `CPLD_ALIGNED RESULT=PASS READY=1`。 |

`ALIGN=1` 是“已对齐”的必要条件，但不是“稳定且受 PPS 约束输出”的充分条件。客户应按上表组合字段判断。CPU/CPLD 内部状态只能证明逻辑已开始输出；若需确认引脚电平已实际到达外部设备，仍应以示波器、计数器或外部采集设备为准。

#### PPS_OUT 运行期相位修正步进

相位修正使用 `0.5us tick` 作为时间基准，但不会每次按 `0.5us` 改动输出。它只在 `ALIGN=1`、PPS_IN 周期合格且 PPS 边沿靠近本地秒边界时，将修正排队到**下一个本地秒装载点**执行：

| PPS_IN 相对本地秒边界的带符号偏差 | 下一秒的修正 | 目的 |
| --- | --- | --- |
| 绝对值 `<=3us` | `0us` | 死区，不追逐采样量化和微小抖动。 |
| 绝对值 `>3us` 且 `<=30us` | `+2us` 或 `-2us` | 温和收敛；每次有效 PPS 最多移动 2us。 |
| 绝对值 `>30us` | `+30us` 或 `-30us` | 明显偏差时快速拉回；每次有效 PPS 最多移动 30us。 |
| 不在本地秒边界附近 | `0us` | 不猜测早晚方向，避免错误校正。 |

PPS_IN 比本地秒边界早时，下一秒缩短；PPS_IN 比本地秒边界晚时，下一秒延长。该修正只改变下一秒的本地计数长度，不会额外触发、抑制或提前释放一拍 PPS_OUT。PPS_IN 丢失后，待执行修正会清除，计数器保持最后一次校准值进入守时。

## 4. 详细查询字段说明

### 输出与 PPS

#### `GET PERIOD`

| 字段 | 值和含义 |
| --- | --- |
| `PERIOD` | 当前生效 PPS_OUT 周期，单位秒。 |
| `PENDING` | `1`：存在待生效周期；`0`：无待生效周期。 |
| `PPAUSE` | `1`：周期切换期间输出暂停；`0`：未暂停。 |
| `PPERIOD` | `PENDING=1` 时的新周期，单位秒；否则为 `0`。 |
| `PCONF` | `1`：正在等待 PPS 对齐确认以完成周期切换；`0`：未处于该阶段。 |

#### `GET OUT`

| 字段 | 值和含义 |
| --- | --- |
| `EN` | `1`：输出已使能；`0`：输出关闭。不是对齐结论。 |
| `STATE` | `0`：输出关闭；`1`：等待 GPS/目标 UTC；`2`：等待 PPS 对齐；`3`：运行中；`4`：未知错误状态。 |
| `PERIOD` / `WIDTH` | 当前周期（秒）/脉宽（毫秒）。 |
| `NEXT` | GPS UTC 有效时，按当前周期计算的下一个整周期 UTC 秒；无有效 UTC 时为 `0`。 |
| `CNT` / `SCNT` | CPLD 输出计数 / 启动输出脉冲计数。对齐后应随输出递增。 |
| `PPSCNT` | CPLD 观测到的 PPS_IN 上升沿累计计数。 |
| `PINT_HALFUS` / `PINT_US` | 最近相邻 PPS_IN 的周期，单位 0.5 us / 1 us。标称 1 秒附近；用于诊断，不表示 PPS_OUT 偏差。 |
| `PSEEN` / `ARM` / `HIGH` | `PSEEN=1`：已见 PPS_IN；`ARM=1`：等待 PPS 触发对齐；`HIGH=1`：采样瞬间 PPS_OUT 正处于高电平。 |
| `ALIGN` / `HOLD` / `BAD` / `RESYNC` | 均为 `0/1`：已对齐 / PPS 丢失守时 / PPS 周期异常 / 请求重同步。对外“可工作”时应为 `1/0/0/0`。 |
| `PWIN_TO` | `1`：计划 PPS 窗口超时；`0`：无该超时。 |
| `PENDING` / `PPAUSE` / `PPERIOD` / `PCONF` | 与 `GET PERIOD` 同义。 |
| `STATUS` / `RAW` | 原始 CPLD 状态/调试寄存器，十六进制，仅供底层工程定位。客户不应依赖位定义。 |
| `UART_BYTES` / `GNRMC_OK` | CPLD GPS UART 当前接收字节计数 / 有效 GNRMC 饱和计数（0 至 15），仅诊断用。 |
| `MATCH` / `LAST_RMC` / `PLAN` / `WAIT_PPS` | CPLD RMC 是否命中当前计划 / 最近 RMC 的 BCD 时间 / 是否存在计划 / 是否等待 PPS；仅在分析对齐失败时使用。 |

#### `GET PPS`

| 字段 | 值和含义 |
| --- | --- |
| `SEEN` | `1`：CPLD 健康窗口内已见 PPS_IN；`0`：PPS_IN 丢失或未见。 |
| `ALIGN` / `HOLD` / `BAD` / `RESYNC` | 与 `GET OUT` 相同，均为 `0/1`。 |
| `CNT` | CPLD PPS_IN 上升沿累计计数。 |
| `CPU_SEEN` / `CPU_CNT` / `CPU_AGE_MS` | CPU 是否已见 PPS / CPU 侧 PPS 累计计数 / 距最近 CPU PPS 的毫秒数。`CPU_AGE_MS` 增长明显时说明 CPU 未再收到 PPS。 |

#### `GET VERIFY`

| 字段 | 值和含义 |
| --- | --- |
| `A_VALID` | `1`：验证锚点 A 有效；`0`：尚无有效锚点。 |
| `A_PPS` | 锚点 A 时的 PPS 计数。 |
| `REQ` / `PLAN` / `MATCH` / `TIMEOUT` | 验证请求存在 / 已有验证计划 / 当前 RMC 匹配验证计划 / 验证等待超时，均为 `0/1`。 |
| `RESULT` | `1`：最近一次验证通过；`0`：未通过或尚无有效结果，需结合 `REQ`、`TIMEOUT` 和主动 `CPLD_VERIFY DONE=FAIL` 判断。 |
| `PPS_DELTA` | 两验证锚点之间实际经历的 PPS 数，用于与预期周期比较。 |

`GET OUT`、`GET STATUS`、`GET PPS`、`GET SYNC` 的 `HOLD` 均为统一的 `0/1` 守时状态。

### GPS、定位和 RMC

#### `GET GPS`、`GET FIX`、`GET UTC`、`GET POS`、`GET SNR`

| 字段 | 值和含义 |
| --- | --- |
| `ONLINE` | `1`：GPS 在线；`0`：GPS/RMC 超时。 |
| `FIX` | `1`：综合定位有效；`0`：定位无效。 |
| `PPS` | `1`：CPLD 看到了 PPS_IN；`0`：未看到或已丢失。 |
| `RMC` / `RMC_READY` | `A/V`：最近 RMC 有效/无效；`1/0`：RMC 已/未达到可参与同步的连续性条件。 |
| `RMC_AGE_MS` | 最近有效 RMC 距当前的毫秒数，越小越新。 |
| `RMC_VALID` / `RMC_TOTAL` | 有效 RMC 行数 / 收到的 RMC 总行数，累计计数。 |
| `UTC_SEQ` / `UTC_CONSEC` | 有效 UTC 序号 / 连续有效 UTC 次数。 |
| `RMC_PHASE_VALID` / `RMC_PHASE_MS` / `RMC_OFFSET` | RMC 相对 CPU PPS 的相位测量是否有效 / 相位毫秒数 / 用于计划的秒偏移；主要用于诊断。 |
| `BAUD` | 当前 GPS UART 波特率。 |
| `UART_ERR`、`FRAME`、`PARITY`、`BREAK`、`OVERRUN`、`CSUM`、`RING_DROP` | GPS UART/NMEA 的累计错误计数。记录基线后观察是否持续增长；非零历史值不一定代表当前故障。 |
| `SNRAVG/MAX/COUNT/VIEW` | 平均/最大信噪比、参与统计数量、可见卫星数量。 |
| `utc` / `UNIX` | UTC 文本 / 对应 UNIX 秒；无有效 UTC 时文本为 `utc=invalid` 且无有效 UNIX。 |
| `QUALITY` | GGA 定位质量：`0` 无定位；`1` GPS 单点；`2` DGPS；其他值按 GPS 接收机 NMEA 定义。 |
| `TYPE` | GSA 定位类型：`1` 无定位；`2` 二维定位；`3` 三维定位；`0` 表示该字段尚未获得。 |
| `SATS` | 在用卫星数。 |
| `LAT/LON` | 纬度/经度及半球方向；无位置时为 `NA ?`。 |
| `AVG/MAX/COUNT/VIEW` | `GET SNR` 的平均/最大信噪比、参与统计数量、可见卫星数。 |

| `SNAP_RMC_AGE_1024US` / `SNAP_RMC_AGE_US_APPROX` | 快照时 RMC 年龄，单位 1024 us / 近似 us。 |

| 字段 | 值和含义 |
| --- | --- |

| `READY` | `1`：GPS 在线、定位有效且 RMC UTC 可用于同步；`0`：尚不具备同步条件。 |

| `NEXT_RESYNC` | CPU 计划的下一次重同步 UTC；不需要时为 `0`。 |
| `APP_VER/APP_BUILD/BOOT_VER/BOOT_BUILD/CPLD_VER/CPLD_BUILD` | `GET VERSION` 的 APP、BOOT、CPLD 版本与构建标识，用于交付核对。 |
| `DEBUG` | `1`：调试日志已开启；`0`：关闭。 |
| `PC_RING_DROP` | PC 命令串口接收缓冲的累计丢弃计数；应为 `0` 或保持不增长。 |

## 5. CPU 主动事件

以下事件无需主机发送命令，默认打印：

| 事件 | 触发时机 | 关键字段 |
| --- | --- | --- |
| `EVENT PPS_LOST HOLD=1 ...` | CPLD 首次判定 PPS_IN 丢失并进入守时。 | `BAD`、`RESYNC`、`ALIGN` |
| `EVENT PPS_LOST RECOVERED ...` | PPS_IN 从丢失状态恢复。 | `DURATION_MS`、`LONG`、`OUT`、`ACTION`，短丢失时还包含 `ALIGN`、`RESYNC`、`READY`。 |
| `EVENT PPS_BAD ...` | PPS_IN 周期异常首次被 CPLD 判定。 | `HOLD`、`RESYNC`、`ALIGN`、`PINT_*` |
| `EVENT PPS_BAD RECOVERED ...` | PPS_IN 周期异常恢复。 | `RESYNC`、`ALIGN`、`PINT_*` |
| `EVENT RMC_TIMEOUT ...` | 曾可用于同步的 RMC 超时。 | `age_ms`、RMC 计数、UART/校验和/环形缓冲错误 |
| `EVENT CPLD_ALIGNED RESULT=PASS READY=1 ...` | CPU/CPLD 完成一次新的对齐，输出进入可工作状态。 | `RESULT`、`READY`、`OUT`、`ALIGN`、`UTC`、`PPS_CNT`、`PERIOD` |
| `EVENT APP_WDOG TIMEOUT_MS=10000 RESET_CAUSE=...` | APP 启动时报告 10 秒硬件看门狗状态。 | `RESET_CAUSE=WDOG`：本次由看门狗复位；`OTHER`：其他复位来源。 |
| `EVENT CPLD_VERIFY DONE=FAIL ...` | 对齐后的周期验证失败。 | 预期/实际 PPS 数、锚点 UTC、等待时间、PPS 周期 |

`DEBUG ON` 后还会输出 `GPS STATUS`、`SYNC STATUS`、`SYNC EVENT`、`VERIFY` 等过程日志；验证通过的 `EVENT CPLD_VERIFY DONE=PASS` 只在此模式输出。验证失败仍为默认主动事件。这些调试日志字段可随版本扩展；上级系统不应依赖它们作正式业务判断。

PPS 丢失恢复有两种结果：

1. **短丢失**：`EVENT PPS_LOST RECOVERED DURATION_MS=<...> LONG=0 ... READY=1` 表示 CPLD 在守时期间仍保持对齐，PPS 已恢复，输出可继续工作，不会再出现新的 `CPLD_ALIGNED`。
2. **长丢失（30 秒或以上）**：`EVENT PPS_LOST RECOVERED DURATION_MS=<...> LONG=1 OUT=0 ACTION=REACQUIRE` 表示系统在 PPS 恢复后已停止旧的守时输出、丢弃旧对齐和旧校准，并开始新的 UTC/PPS 对齐。丢失期间不会自动关闭 PPS_OUT；只在恢复后为避免把长时间累计偏差带入校准而静默重对齐。主机必须等待后续 `EVENT CPLD_ALIGNED RESULT=PASS READY=1 OUT=1 ALIGN=1`，该事件才表示新输出开始且可以工作。
3. **客户已手动关闭输出**：`EVENT PPS_LOST RECOVERED ... OUT=0 ACTION=OUT_ON` 表示 PPS_IN 已恢复，但 APP 不会擅自打开 PPS_OUT。客户可在 GPS 状态正常后发送 `OUT ON`；该命令会走一次新的对齐流程，仍应等待 `CPLD_ALIGNED ... READY=1`。

### 5.1 启动和致命错误消息

| 输出模式 | 输出时机与含义 | 客户处理 |
| --- | --- | --- |
| `APP ready.` 与 `VER=... BUILD=...` | CPU APP 已启动，后续一行给出 APP 构建标识。 | 记录版本；这不代表 GPS 或 PPS 已就绪。 |
| `CPLD ready.` 与 `VER=... BUILD=...` | CPU 已通过 CPLD MAGIC/ECHO 自检并读到 CPLD 构建信息。 | 可继续等待 GPS 与对齐。 |
| `ERROR: CPLD user_ip is not responding. Expected ...` | 读取 CPLD MAGIC 失败，CPU 无法与 CPLD 用户 IP 通信。 | 致命错误；检查 CPLD 位流、板级连接和 CPU/CPLD 复位。 |
| `ERROR: CPLD echo register mismatch.` | CPLD ECHO 寄存器读写自检失败。 | 致命错误；不要开始 PPS 业务，重新烧录/检查硬件。 |

发生上述两类 `ERROR:` 后，APP 保持在故障循环，不能提供正常 PPS 服务。

### 5.2 命令确认和命令错误

所有 `GET` 成功回复都以 `OK` 开头，具体字段在第 2 至第 4 节定义。配置类命令的标准确认如下：

| 输出模式 | 含义 |
| --- | --- |
| `OK PERIOD=...` | 周期设置已被 CPU 接受；结合 `PENDING` 判断是否在等待生效。 |
| `OK WIDTH=...` | 脉宽设置已被 CPU 接受。 |
| `OK OUT EN=1/0` | 输出已被使能/关闭。`OUT ON` 后仍需等 `CPLD_ALIGNED ... READY=1` 才表示可工作。 |
| `OK DEBUG=1/0` | 额外过程日志已开启/关闭。 |
| `OK RMC_DIAG CLEARED` | RMC 诊断饱和计数已清零。 |
| `OK RESET GPS` | 已对 GPS 发出复位脉冲，不代表定位已恢复。 |
| `OK ENTER BOOT` | 已写入进入 BOOT 的标志；重启后的行为由 BOOT 决定。 |
| `ERR BAD PERIOD` | 周期为 0、超出允许范围或格式非法。 |
| `ERR BAD WIDTH` | 脉宽超出允许范围或格式非法。 |
| `ERR BAD TARGET` | 指定的 `target_utc` 无效、已过去或不符合周期边界。 |
| `ERR ENTER BOOT WRITE` | 写 BOOT 参数失败。 |
| `ERR LINE TOO LONG` | PC 串口接收的一行超过缓冲区长度。 |
| `ERR UNSUPPORTED` | 命令、子命令或参数组合不受支持。 |

### 5.3 `DEBUG ON` 过程日志字典

以下消息只在 `DEBUG ON` 时输出，除非明确标记为启动致命错误。它们用于工程定位，客户不应把某个具体字段当作长期稳定业务 API。

| 输出前缀/模式 | 触发条件与含义 |
| --- | --- |
| `AG32 GPS PPS P3 pre-check start/passed` | CPU 启动时的 CPLD 自检开始/通过。 |
| `CPLD MAGIC=...`、`CPLD ECHO write=... read=...` | CPLD MAGIC 与 ECHO 自检的原始值。 |
| `CPLD P3 configured CTRL=...` | CPU 写入 CPLD 初始周期、脉宽和控制寄存器后的寄存器快照。 |
| `Waiting GPS_PPS_IN on PIN_10 ...` | 启动后等待 GPS PPS 的引脚和当前输出配置提示。 |
| `GPS reset pulsed on PIN_14 ...` | 已发出 GPS 复位脉冲及 UART 引脚信息。 |
| `GPS EVENT uart_baud=... fixed` | GPS UART 波特率自动探测并固定。 |
| `GPS RAW: $...` | 预算内的原始 GPS/NMEA 行，仅供协议排查。 |
| `GPS STATUS online=... fix=...` | 周期性 GPS 汇总：在线、定位、RMC、定位质量、卫星、RMC 年龄、UART 和 SNR 计数。 |
| `SYNC STATUS state=...` | 周期性同步状态机汇总：就绪、PPS、对齐、守时、异常、目标 UTC 和下次重同步。 |
| `SYNC EVENT state=...` | CPU 同步状态机状态转换。 |
| `SYNC EVENT rmc_utc_ready/...restart` | 连续有效 RMC UTC 已达到同步条件，或连续性被打断。 |
| `SYNC EVENT request_latched ...` | CPU 已锁存一次对齐/重同步请求，等待后续 RMC/PPS 计划。 |
| `SYNC EVENT plan ...`、`plan_target ...` | CPU 已计算并写入 CPLD 的对齐计划。 |
| `SYNC EVENT plan_invalid/...wait_next_day/...stale_plan` | 计划无效、需等下一天或计划已过期。 |
| `SYNC EVENT wait_pps_without_plan ...` | 目标 UTC 已过但 CPLD 未接受 PPS，需要重新规划。 |
| `EVENT CPLD_PLAN_PPS_TIMEOUT ...` | CPLD 计划 PPS 窗口超时，CPU 已丢弃旧计划并重新规划。 |
| `EVENT CPLD_RESYNC REQUEST ...` | CPLD 请求重同步；`reason` 给出 `INIT`、`PPS_LOST`、`PPS_BAD` 或周期切换等原因。 |
| `SYNC EVENT holdover/...holdover_recovered/...holdover_resume` | CPU 观察到守时、守时恢复，或恢复运行状态。 |
| `SYNC EVENT aligned/...aligned_debug` | 与对齐相关的内部过程日志；客户应以默认的 `EVENT CPLD_ALIGNED RESULT=PASS READY=1` 为准。 |
| `VERIFY plan ...`、`VERIFY wait_next_day ...` | 周期验证计划的内部过程。 |
| `EVENT CPLD_VERIFY DONE=PASS ...` | 周期验证通过；默认关闭，只在调试模式输出。 |
| `BOOT PARAM write failed during APP startup` | APP 启动时维护 BOOT 参数失败；需检查非易失存储或 BOOT 参数区域。 |

### 5.4 仅测试构建会出现的输出

下列输出只在源码编译开关 `PIN21_GPIO_SMOKE_TEST` 或 `UART1_LOOPBACK_TEST` 打开时出现，不属于正常 APP 运行协议：

| 输出前缀 | 含义 |
| --- | --- |
| `PIN_21 GPIO smoke test ...`、`PIN_21 GPIO level=...` | PIN_21 GPIO 波形冒烟测试。 |
| `UART1 loopback test start ...`、`UART1 LOOP TX/RX[...]` | UART1 外部回环测试。 |

客户正式运行固件时不应看到这些消息；若看到，说明烧录了测试构建而非业务 APP。

## 6. 当前接口缺口与建议

1. **缺少定位边沿事件。** 当前没有默认的 `EVENT GPS_FIX_ACQUIRED`、`EVENT GPS_FIX_LOST`、`EVENT GPS_ONLINE/OFFLINE`；定位变化只能通过 `GET STATUS` 或 `GET FIX` 轮询获得。建议增加一次性边沿事件，携带 UTC、定位质量、类型、卫星数和 RMC 年龄。
2. **事件缺少统一时间戳。** `CPLD_ALIGNED` 自带 UTC，其余事件大多没有。建议每个 `EVENT` 同时带 `UTC=<...>`（可用时）和 `UP_MS=<...>`（单调启动毫秒）。
3. **定义机器可解析的行结束。** 当前固件输出为换行。建议协议正式固定为 `CRLF`，并要求上位机兼容 `LF`。
4. **增加协议版本。** 建议 `GET VERSION` 增加 `PROTO_VER=<major.minor>`；字段新增只增加次版本，破坏性变更增加主版本。
5. **字段单位规范。** 所有布尔字段固定为 `0/1`，所有时长字段应带 `_MS`、`_US` 后缀。
6. **关键错误分级。** 建议标准化 `EVENT ALARM=<INFO|WARN|ERROR>`，让上级快速订阅 `WARN/ERROR`。
7. **命令关联号。** 若未来有多主机或异步事件并发，建议命令支持可选 `ID`，回复携带同一 `ID`，避免响应与事件混淆。

## 7. 上级软件建议流程

1. 连接后发送 `GET VERSION`、`GET STATUS`，记录版本与初始状态。
2. 正常运行中低频轮询 `GET STATUS`，并实时解析所有 `EVENT` 行。
3. 发生 `GPS=0`、`PPS=0`、`FIX=0`、`ALIGN=0`、`HOLD=1`、`BAD=1`、`RESYNC=1` 或 `CPLD_VERIFY DONE=FAIL` 时，保存上下文并调用 `GET GPS`、`GET PPS`、`GET OUT`、`GET SYNC`、`GET RMC DIAG` 获取详细证据。
4. 对 `UART_ERR`、`FRAME`、`CSUM`、`RING_DROP`、`PC_RING_DROP` 保存前后差分；仅在计数持续增长时判定链路问题。

## 8. 已有 DUT 的串口升级（Linux）

本节面向已安装 BOOT 的 DUT。客户不需要源码、PlatformIO、OpenOCD，也不需要执行空片烧录流程；日常只通过设备串口升级 APP 或 CPLD。

### 8.1 交付给客户的文件

| 文件 | 用途 |
| --- | --- |
| `ag32_boot_tool.py` | Python 3 串口升级工具，来源：`boot/tools/ag32_boot_tool.py`。 |
| `requirements.txt` | Python 依赖，当前仅为 `pyserial`。 |
| `<app_release>.bin` | APP 升级二进制文件。 |
| `<cpld_release>.bin` | CPLD 位流升级二进制文件。 |
| 发行说明 | 写明 APP/CPLD 版本号、适用 BOOT 协议版本、SHA-256、升级顺序和变更内容。 |

不要向客户交付源文件、OpenOCD 或首次烧录脚本。升级工具会为原始 `.bin` 自动生成传输头、分块写入并验证 CRC32。

### 8.2 Linux 环境准备

```bash
python3 -m venv .venv
. .venv/bin/activate
python3 -m pip install -r requirements.txt
```

使用稳定的设备路径，例如 `/dev/serial/by-id/...`，不要依赖可能变化的 `/dev/ttyUSB0`。普通用户需要串口访问权限，例如加入 `dialout` 组后重新登录：

```bash
sudo usermod -aG dialout "$USER"
```

### 8.3 升级前检查

工具使用 115200、8N1。`--enter-boot` 会先通过 APP 串口发送 `ENTER BOOT`，再等待 BOOT 就绪。升级前可先查询 BOOT 能力：

```bash
python3 ag32_boot_tool.py \
  --port /dev/serial/by-id/<DUT> \
  info --enter-boot
```

期望看到 `INFO OK`，并确认 `proto_version`、`support_image_mask`、`app_size`、`logic_size` 与发行说明兼容。若此步骤失败，不要开始传输镜像。

### 8.4 升级 APP

```bash
python3 ag32_boot_tool.py \
  --port /dev/serial/by-id/<DUT> \
  upgrade-app \
  --bin <app_release>.bin \
  --image-version 0xYYYYMMDD \
  --enter-boot
```

成功标志依次为 `HELLO`、`INFO OK`、`START OK`、若干 `DATA n/N`、`END OK image_crc32=...` 和 `UPGRADE OK (reboot requested)`。`END OK` 表示设备已完成完整镜像 CRC32 校验；重启后再用 APP 串口 `GET VERSION` 确认版本。

### 8.5 升级 CPLD

```bash
python3 ag32_boot_tool.py \
  --port /dev/serial/by-id/<DUT> \
  upgrade-cpld \
  --bin <cpld_release>.bin \
  --image-version 0xYYYYMMDD \
  --enter-boot
```

`upgrade-logic` 是 `upgrade-cpld` 的同义命令。成功后使用 APP 串口 `GET VERSION` 确认 `CPLD_VER/CPLD_BUILD`，再用 `GET STATUS` 确认 CPU 与 CPLD 正常通信。

### 8.6 失败处理和限制

| 工具/设备输出 | 含义和处理 |
| --- | --- |
| `ERROR: missing dependency 'pyserial'` | 安装 `requirements.txt`。 |
| `timeout waiting for boot response` | 检查串口路径、权限、波特率，确认当前 APP 支持 `ENTER BOOT`。 |
| `protocol mismatch` | 升级工具与 DUT BOOT 协议版本不兼容；使用匹配版本的工具。 |
| `device does not support APP/CPLD` | BOOT 报告的镜像类型能力不匹配，不要强制升级。 |
| `image too large` / `invalid target` | 使用错误镜像或不适配当前 DUT 分区。 |
| `boot returned NACK ...` | BOOT 拒绝帧、镜像头、序号、范围、Flash 操作或 CRC；保存完整输出并停止升级。 |
| 传输中断 | APP 升级中断后 APP 可能无效，需重新完成 APP 升级；CPLD 升级中断不会使 APP 失效，可重新发送 CPLD 镜像。 |

日常升级无需任何 JTAG、CMSIS-DAP 或 OpenOCD 操作。一次只升级一个镜像；若发行说明要求同时升级，建议先升级 CPLD、确认 APP 可正常启动后再升级 APP，或严格按该发行说明指定顺序执行。
