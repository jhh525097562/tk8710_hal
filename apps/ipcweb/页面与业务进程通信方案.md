# 页面与业务进程通信方案

## 1. 方案目标

本方案用于实现 Web 页面按钮触发已有业务进程执行耗时任务，并在任务完成后由页面读取任务结果。

目标流程如下：

```text
页面按钮
  ↓ HTTP API
web_server.c
  ↓ Unix Domain Socket
已有业务进程
  ↓ 执行数据获取或处理任务
状态文件 / 结果文件
  ↓ HTTP API
页面轮询状态并读取结果
```

本方案适用于当前工程的技术框架：

- Web 服务端基于 C 语言和 Mongoose。
- 页面资源位于 `web_resources/html/` 和 `web_resources/css/`。
- HTML/CSS 由 `tools/gen_resources.py` 生成到 `inc/web_resources.h`。
- 页面通过 `web_server.c` 中的 `send_page_start()`、`send_chunk()`、`send_page_end()` 进行分块渲染。
- API 路由统一在 `web_server.c` 的 `event_handler()` 中通过 `mg_http_match_uri()` 分发。
- 前端使用原生 HTML/CSS/JavaScript，不使用 React/Vue 等前端框架。

## 2. 术语说明

为避免混淆，本文档统一使用以下术语：

| 术语 | 含义 |
|---|---|
| Web 服务端 | 当前工程中的 `web_server.c`，负责 HTTP 页面渲染和 API 响应 |
| IPC 服务端 | 集成到已有业务进程中的 Unix Domain Socket Server |
| IPC 客户端 | 集成到 `web_server.c` 中的 Unix Domain Socket Client |
| 业务进程 | 已有的后台进程，负责真正执行数据获取或处理任务 |
| 状态文件 | 业务进程写出的任务状态文件，供 Web 服务端查询 |
| 结果文件 | 业务进程写出的任务结果文件，供 Web 服务端返回给页面 |

## 3. 总体架构

推荐架构如下：

```text
浏览器页面
  ↓
POST /api/data_collect_start
  ↓
web_server.c
  ↓
IPC 客户端连接 /tmp/data_collect.sock
  ↓
业务进程中的 IPC 服务端
  ↓
业务回调函数启动耗时任务
  ↓
业务进程写状态文件和结果文件
  ↓
页面通过 /api/data_collect_status 轮询状态
  ↓
任务完成后通过 /api/data_collect_result 读取结果
```

推荐分工如下：

| 模块 | 职责 |
|---|---|
| 页面 | 提供按钮、显示任务状态、显示结果 |
| `web_server.c` | 提供 HTTP API、调用 IPC 客户端、读取状态文件和结果文件 |
| IPC 客户端 | 连接 Unix Socket，向业务进程发送命令 |
| IPC 服务端 | 监听 Unix Socket，接收命令并调用业务回调 |
| 业务进程 | 执行耗时任务，维护任务状态，生成结果文件 |

## 4. Unix Socket 通信模型

推荐使用 Unix Domain Socket 作为 Web 服务端与业务进程之间的本机进程间通信机制。

通信方向为：

```text
web_server.c = IPC 客户端
业务进程 = IPC 服务端
```

这样设计的原因：

1. 业务进程是实际任务执行者，最清楚当前是否空闲、是否正在执行、是否可以接受新任务。
2. `web_server.c` 只负责接收页面请求和发送控制命令，不承担业务状态机。
3. 业务进程可以统一维护 `idle`、`running`、`done`、`failed` 等状态。
4. 页面请求不需要等待任务执行完成，只等待业务进程快速确认命令是否被接受。

推荐 Socket 路径：

```text
/tmp/data_collect.sock
```

如后续存在多个任务，可以按任务区分：

```text
/tmp/diagnose.sock
/tmp/data_collect.sock
/tmp/scan.sock
```

也可以使用一个统一 Socket，并通过命令字符串区分任务。

## 5. IPC 服务端模块设计

IPC 服务端模块应集成到已有业务进程中，不建议直接放入当前 Web 工程 `src/` 目录。

原因是当前 Web 工程的 `Makefile` 使用：

```makefile
SRCS = $(wildcard $(SRC_DIR)/*.c)
```

这意味着放入 `src/` 的所有 `.c` 文件都会被编译进 `web_server`。而 IPC 服务端模块是给业务进程使用的，不应该默认编译进 Web 服务端。

建议文件组织：

```text
业务进程工程：
  ipc_command_server.c
  ipc_command_server.h

当前 Web 工程：
  src/ipc_command_client.c
  inc/ipc_command_client.h
```

如果只是先保存通用代码模板，应放在不被当前 Makefile 自动编译的位置，或者后续修改 Makefile 明确区分 Web 侧和业务进程侧源码。

### 5.1 IPC 服务端职责

IPC 服务端模块只负责通用通信，不负责具体业务。

应负责：

```text
socket()
bind()
listen()
accept()
read()
调用业务回调
write()
close()
```

不应负责：

```text
具体数据采集
结果文件格式
页面展示逻辑
HTTP API 返回格式
```

### 5.2 推荐接口形式

业务进程集成时建议使用回调方式：

```c
typedef enum {
    IPC_CMD_RESULT_OK = 0,
    IPC_CMD_RESULT_BUSY = 1,
    IPC_CMD_RESULT_ERROR = 2,
} ipc_cmd_result_t;

typedef ipc_cmd_result_t (*ipc_cmd_callback_t)(const char *cmd, void *user_data);

typedef struct {
    const char *socket_path;
    ipc_cmd_callback_t on_command;
    void *user_data;
} ipc_server_config_t;

int ipc_server_start(const ipc_server_config_t *config);
void ipc_server_stop(void);
```

业务进程示例：

```c
static ipc_cmd_result_t handle_ipc_command(const char *cmd, void *user_data)
{
    if (strcmp(cmd, "START") == 0) {
        return start_data_collect_task();
    }

    if (strcmp(cmd, "PING") == 0) {
        return IPC_CMD_RESULT_OK;
    }

    return IPC_CMD_RESULT_ERROR;
}

int main(void)
{
    ipc_server_config_t config = {
        .socket_path = "/tmp/data_collect.sock",
        .on_command = handle_ipc_command,
        .user_data = NULL,
    };

    ipc_server_start(&config);

    while (1) {
        run_business_loop();
    }

    ipc_server_stop();
    return 0;
}
```

### 5.3 IPC 服务端运行方式

推荐 IPC 服务端内部使用独立线程监听 Socket：

```text
业务主线程：继续执行原有业务逻辑
IPC 线程：监听 Unix Socket，接收 Web 侧命令
```

优点：

1. 对已有业务进程侵入小。
2. 不需要改造原有主循环。
3. Web 页面可随时触发命令。

注意事项：

1. 业务状态变量需要线程安全保护。
2. `START` 回调中不要直接执行耗时任务，应快速设置任务标志或启动后台任务后返回。
3. 如果当前任务正在执行，应返回 `BUSY`。

## 6. IPC 命令协议

第一版建议使用简单文本协议，不引入复杂 JSON 协议。

### 6.1 Web 服务端发送命令

```text
START\n
```

可选命令：

```text
PING\n
STATUS\n
STOP\n
```

第一版至少支持：

```text
START
PING
```

### 6.2 业务进程返回响应

```text
OK
BUSY
ERROR reason
```

含义：

| 响应 | 含义 |
|---|---|
| `OK` | 命令已接受，任务已启动或操作成功 |
| `BUSY` | 业务进程当前正在执行任务，不能重复启动 |
| `ERROR reason` | 命令失败，并返回失败原因 |

Web 服务端收到 IPC 响应后，再转换为 HTTP JSON 返回给页面。

## 7. Web API 接口设计

结合当前工程已有接口风格，第一版推荐使用下划线风格的 `/api/` 接口。

推荐接口：

```text
POST /api/data_collect_start
GET  /api/data_collect_status
GET  /api/data_collect_result
```

可选接口：

```text
GET  /api/data_collect_result_download
POST /api/data_collect_stop
```

### 7.1 启动任务接口

```text
POST /api/data_collect_start
```

职责：

1. 校验用户已登录。
2. 连接 `/tmp/data_collect.sock`。
3. 发送 `START` 命令。
4. 等待业务进程快速响应。
5. 将 `OK` / `BUSY` / `ERROR` 转换为 JSON 返回页面。

成功响应示例：

```json
{
  "success": true,
  "state": "running",
  "message": "任务已启动"
}
```

业务繁忙响应示例：

```json
{
  "success": false,
  "state": "busy",
  "message": "任务正在执行中，请勿重复触发"
}
```

业务进程未启动响应示例：

```json
{
  "success": false,
  "state": "error",
  "message": "业务进程未启动或 IPC 连接失败"
}
```

### 7.2 查询状态接口

```text
GET /api/data_collect_status
```

职责：

1. 读取状态文件。
2. 如果状态文件不存在，返回 `idle`。
3. 设置 `Cache-Control: no-store`，避免浏览器缓存。
4. 返回 JSON 状态。

状态文件不存在时响应示例：

```json
{
  "state": "idle",
  "message": "尚未执行任务",
  "result_ready": false
}
```

任务执行中响应示例：

```json
{
  "state": "running",
  "message": "正在采集数据",
  "result_ready": false
}
```

任务完成响应示例：

```json
{
  "state": "done",
  "message": "任务完成",
  "result_ready": true
}
```

任务失败响应示例：

```json
{
  "state": "failed",
  "message": "任务执行失败",
  "result_ready": false
}
```

### 7.3 读取结果接口

```text
GET /api/data_collect_result
```

职责：

1. 检查状态是否为 `done`。
2. 检查结果文件是否存在。
3. 读取结果文件。
4. 返回给页面展示。

如果结果文件较小，可以直接返回 JSON：

```text
Content-Type: application/json; charset=utf-8
Cache-Control: no-store
```

如果结果是文本报告，可以返回：

```text
Content-Type: text/plain; charset=utf-8
Cache-Control: no-store
```

如果结果文件较大，不建议一次性读入内存，应增加下载接口：

```text
GET /api/data_collect_result_download
```

并采用类似日志下载接口的方式，边读文件边通过 `mg_send()` 输出，避免大 buffer 占用内存。

## 8. 页面入口设计

不建议第一版强制新增独立页面 `/data_collect`。

当前工程已有页面路由：

```text
/status
/config
/manger
/network
/upgrade
```

公共导航的 active 状态目前也只覆盖已有页面类型。因此第一版更推荐将功能作为一个卡片集成到已有页面中。

推荐放置原则：

| 功能类型 | 推荐页面 |
|---|---|
| 设备维护、手动触发、日志/结果查看 | `/upgrade` 或 `/manger` |
| 系统诊断、状态采集 | `/status` |
| 参数配置触发类任务 | `/config` |
| 网络相关任务 | `/network` |

如果后续确实需要独立页面，再新增：

```text
GET /data_collect
```

并同步修改：

1. `web_resources/html/layout_header.html`
2. `send_page_start()` 的 active 参数处理
3. 新增 `web_resources/html/data_collect.html`
4. 新增 `handle_data_collect()`
5. `event_handler()` 中新增页面路由

## 9. 前端轮询设计

页面点击按钮后，不应等待任务完成，而应采用异步轮询。

推荐流程：

```text
1. 用户点击按钮
2. 禁用按钮，显示“任务启动中”
3. POST /api/data_collect_start
4. 如果返回 running：开始轮询 /api/data_collect_status
5. 如果返回 busy：显示任务正在执行，并继续轮询状态
6. 如果返回 error：显示错误并恢复按钮
7. 状态变为 done：停止轮询，请求 /api/data_collect_result
8. 状态变为 failed：停止轮询，显示失败原因
```

当前工程已有前端轮询经验，推荐沿用以下模式：

```text
setTimeout + inFlight + document.hidden + AbortController
```

不推荐简单使用固定 `setInterval`，原因是如果上一次请求未完成，下一次请求又发出，可能导致请求堆积。

推荐原则：

1. 每次请求完成后再安排下一次请求。
2. 使用 `inFlight` 防止重复请求。
3. 页面隐藏时暂停轮询。
4. 页面恢复显示时继续轮询。
5. 每次 fetch 增加超时控制。

轮询间隔建议：

```text
1 秒到 2 秒
```

如果任务耗时较长，可以在连续运行一段时间后降低轮询频率。

## 10. 状态文件和结果文件设计

第一版推荐使用 `/tmp` 保存运行期状态：

```text
/tmp/data_collect_status.json
/tmp/data_collect_result.json
```

如果结果需要掉电保存或供用户后续下载，建议改为：

```text
/userdata/data_collect/status.json
/userdata/data_collect/result.json
```

### 10.1 状态文件格式

推荐状态文件内容：

```json
{
  "state": "running",
  "message": "正在采集数据",
  "updated_at": 1710000000,
  "result_ready": false
}
```

状态枚举：

| 状态 | 含义 |
|---|---|
| `idle` | 空闲或尚未执行 |
| `running` | 正在执行 |
| `done` | 执行完成 |
| `failed` | 执行失败 |

### 10.2 结果文件格式

如果结果是结构化数据，推荐 JSON：

```json
{
  "success": true,
  "items": [
    {
      "name": "example",
      "value": "123"
    }
  ]
}
```

如果结果是诊断报告或日志文本，可以使用纯文本文件。

## 11. 文件写入原子性要求

业务进程写状态文件和结果文件时，必须避免 Web 服务端读到半截文件。

推荐写法：

```text
1. 写入临时文件，例如 /tmp/data_collect_result.json.tmp
2. fflush
3. fsync
4. close
5. rename 到 /tmp/data_collect_result.json
```

状态文件也应使用同样方式：

```text
/tmp/data_collect_status.json.tmp
/tmp/data_collect_status.json
```

任务完成时推荐顺序：

```text
1. 写 result.tmp
2. rename 为 result.json
3. 写 status.tmp，状态为 done
4. rename 为 status.json
```

这样页面看到 `done` 时，结果文件一定已经准备好。

## 12. Web 服务端阻塞控制

当前 `web_server.c` 基于 Mongoose 单事件循环运行。

因此，在 HTTP API 中连接 Unix Socket 时必须控制阻塞时间，避免整个 Web 服务卡住。

要求：

1. IPC 客户端连接必须有超时。
2. IPC 客户端读写必须有超时。
3. `POST /api/data_collect_start` 只等待业务进程快速确认，不等待任务完成。
4. 业务进程收到 `START` 后应立即返回 `OK`、`BUSY` 或 `ERROR`。
5. 推荐超时时间为 500ms 到 1000ms。

如果出现以下情况，应立即返回错误 JSON：

```text
socket 文件不存在
connect 超时
write 失败
read 超时
响应格式非法
```

## 13. 异常处理

### 13.1 IPC Socket 不存在

含义：业务进程未启动，或 IPC 服务端初始化失败。

页面提示：

```text
业务进程未启动，请检查服务状态
```

目标板调试建议：

```cmd
ls -l /tmp/data_collect.sock
ps | grep 业务进程名
```

### 13.2 业务进程返回 BUSY

含义：已有任务正在执行。

处理方式：

1. 页面显示“任务正在执行中”。
2. 不重复发送 START。
3. 继续轮询状态接口。

### 13.3 状态为 done 但结果文件不存在

含义：业务进程写文件顺序错误或结果生成失败。

处理方式：

1. Web 服务端返回错误 JSON。
2. 页面提示“结果文件不存在”。
3. 业务进程侧检查写文件流程。

### 13.4 页面刷新

页面加载后可先请求：

```text
GET /api/data_collect_status
```

如果状态为 `running`，页面继续显示执行中并恢复轮询。

如果状态为 `done`，页面可以直接请求结果接口。

如果状态为 `idle` 或状态文件不存在，页面显示初始状态。

## 14. 安全性要求

1. 所有接口必须放在登录校验之后，不允许未登录访问。
2. 新 API 应在 `event_handler()` 的 `is_authed(hm)` 分支下注册。
3. 页面不能直接访问系统文件路径，必须通过 Web API 间接读取。
4. 如果接口支持文件名参数，必须做路径穿越防护。
5. 不允许将用户输入直接拼接到 shell 命令。
6. IPC 命令长度必须限制，例如最大 128 字节。
7. IPC 服务端应拒绝未知命令。

## 15. 推荐实现步骤

### 15.1 业务进程侧

1. 实现 `ipc_command_server.c` 和 `ipc_command_server.h`。
2. 业务进程启动时调用 `ipc_server_start()`。
3. 注册 `on_command` 回调。
4. 收到 `START` 时：
   - 如果任务正在执行，返回 `BUSY`。
   - 如果空闲，写状态 `running`。
   - 启动后台任务。
   - 立即返回 `OK`。
5. 后台任务完成后：
   - 先写结果文件。
   - 再写状态 `done`。
6. 失败时写状态 `failed`。

### 15.2 Web 工程侧

1. 实现 `ipc_command_client.c` 和 `ipc_command_client.h`。
2. 在 `web_server.c` 中新增 API handler：
   - `handle_api_data_collect_start()`
   - `handle_api_data_collect_status()`
   - `handle_api_data_collect_result()`
3. 在 `event_handler()` 的认证分支下增加路由：
   - `/api/data_collect_start`
   - `/api/data_collect_status`
   - `/api/data_collect_result`
4. 在现有页面中新增功能卡片。
5. 前端按钮通过 `fetch()` 调用启动接口。
6. 前端使用轮询方式查询状态。
7. 状态为 `done` 后读取结果并展示。

第一版建议只实现最小闭环：

```text

GET  /api/data_collect_result
```

IPC 命令只支持：

```text
START
PING
```

结果文件先使用 `/tmp`，如果后续需要保存历史结果，再迁移到 `/userdata`。

## 17. 调试建议

在目标板上建议先使用系统常用调试工具确认运行状态。

检查业务进程：

```cmd
ps | grep 业务进程名
```

检查 Unix Socket：

```cmd
ls -l /tmp/data_collect.sock
```

检查状态文件：

```cmd
cat /tmp/data_collect_status.json
```

检查结果文件：

```cmd
ls -l /tmp/data_collect_result.json
cat /tmp/data_collect_result.json
```

检查 Web 服务日志：

```cmd
ps | grep web_server
```

如果业务进程由 SysV init 管理，可检查对应启动脚本：

```cmd
/etc/init.d/服务名 status
```

或直接查看进程是否存在。

```text
Unix Domain Socket

业务进程 IPC 服务端

状态文件 / 结果文件
  ↓
页面轮询读取
```

关键设计点：

1. 业务进程作为 IPC 服务端。
2. `web_server.c` 作为 IPC 客户端。
3. Web API 使用当前工程已有的 `/api/xxx` 风格。
4. 耗时任务采用启动接口、状态轮询接口、结果读取接口。
5. 文件写入使用临时文件加 `rename()`，避免读取半截文件。
6. IPC 客户端必须设置短超时，避免阻塞 Mongoose 主事件循环。
7. 第一版优先集成到已有页面，不强制新增独立页面。
