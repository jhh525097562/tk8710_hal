## 2. 灯语与含义说明（现场速查）

只观察外接指示灯：**绿色RUN表示正常或准备，红色NET表示异常。两色互斥，一种颜色显示时另一种关闭。** 板载D8亮灭相反，不适用下面的颜色说明。

| 灯语 | 含义 | 典型场景 / 排查方向 | 对外状态 |
|---|---|---|---|
| **绿常亮** | 网关正常运行 | 网络有效、MQTT连接及订阅成功、TK8710业务就绪；空闲无数据也正常 | READY |
| **绿单闪** | 正在启动或准备 | 开机初始化、联网、MQTT连接准备、HAL配置 | PREPARING |
| **绿双闪** | 等待NS配置 | 检查NS是否已给此网关下发配置，尚未超出等待期限 | WAIT_NS |
| **绿三闪** | 等待GPS/PPS同步 | GPS搜星/定位、基础同步或输出PPS周期对齐中 | WAIT_GPS |
| **绿均匀慢闪** | 正在执行受控操作 | 扫频或有时限的升级维护 | OPERATION |
| **红常亮** | 无可用网络 | 已确认所有允许使用的网线、4G、WiFi链路均不可用 | NETWORK_FAULT |
| **红单闪** | MQTT消息通道异常 | 检查broker地址、认证、订阅权限和连接；不是仅有TCP连接就算正常 | MQTT_FAULT |
| **红双闪** | 网关配置异常 | NS配置等待超时、参数无效，包括无效GPS开关值 | CONFIG_FAULT |
| **红三闪** | GPS同步异常 | NS要求GPS开启但模块缺失、GPS同步超时、PPS对齐失败或运行健康异常 | GPS_FAULT |
| **红四闪** | 网关业务或监测异常 | HAL/RF/TRM故障、进程反复退出、必要快照缺失/过期且无法进一步归因 | GATEWAY_FAULT |
| **两灯灭或不确定** | 无法仅靠灯判断 | 未供电、灯控未启动/已停止、GPIO控制失败，或恰处于闪烁的熄灭阶段 | NOT_CONTROLLED / 闪烁间隔 |

取消正常收发`txrx`灯语：流量多少不是健康程度。分组短闪亮250ms、组内灭250ms，最后一下熄灭后等待2秒；仅扫频/维护使用亮1秒、灭1秒的均匀慢闪。模式变化从第一下重新开始。
设备健康的条件不包含“有终端正在发送”，空闲但可工作的网关仍绿常亮。

“单/双/三/四闪”指**每组闪1/2/3/4下**，不是每秒闪几次。组周期分别为2.25、2.75、3.25、3.75秒；绿均匀慢闪是固定1秒亮、1秒灭，没有额外组间停顿。
例如绿三闪为：`亮250ms → 灭250ms → 亮250ms → 灭250ms → 亮250ms → 灭2秒 → 重复`。

故障灯显示的是本轮锁存的主要故障类别，普通重启或重新进入等待阶段不会立即清除。全部健康连续30秒后解除红色故障；初次启动全部健康稳定3秒后绿常亮。多个故障同时出现时，按第3章优先级显示一种，不轮流播放。

### 2.1 各种场景下的灯光速查

以下均指外接灯：绿色RUN、红色NET。绿色显示时红色关闭，红色显示时绿色关闭。下表通称“绿闪/红闪”时，具体组数按上表的阶段/故障类别确定，不再统一为均匀慢闪。
表中的“绿闪”以**没有已锁存业务故障、没有更高优先级异常**为前提。若已经红闪锁存，即使进程重新启动并进入等待阶段，通常仍保持红闪，直到三项健康连续30秒。各场景的实板验证范围见第9章，不代表下表全部做过实板故障注入。

| 实际场景 | 灯光过程/最终状态 | 判定说明 |
|---|---|---|
| 刚上电，灯控未运行 | 两灯不保证；新版U-Boot完成LED初始化后应两灯灭 | 初始化前由硬件决定；不能用两灯灭判断具体故障 |
| Linux启动、必要状态文件尚未建立 | 启动宽限内绿闪，超过宽限仍缺少必要状态则红闪 | 网络尚未出现时宽限到开机180秒；网络首次就绪后给其它必要快照30秒出现时间 |
| 网络、MQTT、TK8710全部正常 | 绿闪→绿常亮 | 初次三项健康连续3秒后进入READY |
| 正常运行但没有终端数据 | 绿常亮 | 无业务流量不等于故障 |
| 正常运行且持续收发数据 | 绿常亮 | 已取消旧txrx快闪，不根据包间隔变色 |
| 已联网，MQTT正在连接或等SUBACK | 绿闪；明确失败或等待超过10秒后红闪 | 仅TCP连接或CONNACK成功还不够，必须订阅确认成功 |
| MQTT密码错误、broker拒绝或订阅被拒绝 | 红闪 | 网络有连通性，但业务消息通道不满足就绪条件 |
| MQTT连接断开但系统网络仍可用 | 重连宽限内绿闪，超过10秒未恢复则红闪 | 已锁存业务故障时不重新给予绿闪；收到断连回调即撤销ready |
| TK8710等待NS配置 | 绿闪；无配置超时/退出后按故障或缺失规则转红闪 | 当前网关约3次、每次10秒请求；灯控阶段显示预算35秒 |
| NS配置GPS关闭，网关没有GPS模块 | 等待NS/配置时绿闪，业务就绪后三项健康则绿常亮 | gps_enable=0，允许本地同步；GPS不存在本身不触发红闪 |
| NS配置GPS关闭，网关实际有GPS模块 | 同上：最终可绿常亮 | 按关闭策略使用本地同步，不因模块存在强制等待GPS |
| NS配置GPS打开，但网关没有GPS模块 | 绿闪等待模块探测→故障红闪 | gps_enable=1；不自动回退本地同步，业务拒绝启动。模块不存在通常是通信探测失败，不是必然等待300秒 |
| NS配置GPS打开，模块存在但尚未搜星/定位/PPS基础就绪 | 绿闪；失败或超时后红闪 | wait_gps_sync阶段；业务搜索预算约300秒，灯控显示预算330秒 |
| GPS基础状态正常，等待输出PPS周期对齐 | 绿闪；对齐失败或超时后红闪 | wait_pps_alignment阶段；业务对齐预算60秒，灯控显示预算90秒 |
| GPS/PPS对齐成功，HAL配置启动成功 | 三项健康后绿常亮 | 网关running/business_ready=true仍需网络、MQTT同时就绪 |
| 运行中GPS/PPS异常 | 网关发布degraded或fault后红闪 | 按现有约10秒健康检查及PPS监测结果更新，不保证物理异常瞬间变灯 |
| HAL初始化/启动失败 | 红闪 | 显式fault优先；程序即使被守护重新拉起，也不能直接当作正常 |
| 运行中检测到异常RF通道 | 发布degraded/fault后红闪 | 当前少量异常为degraded，达到现有退出阈值为fault；不等于本次新增了RF检测算法 |
| 缺少TxDC校准文件，但程序仅告警且仍running | 仍可能绿常亮 | 当前没有把“校准文件有效”作为独立就绪门槛，绿色不代表校准或射频性能验收通过 |
| 拔掉网线，当前以太网失效，正在找备用网络 | 绿闪；若确认无可用链路则红常亮 | 新网络观察器约每秒检测carrier/IP；实际路由切换仍由守护原有逻辑执行 |
| 网线未插，但4G或WiFi已成为有效活跃链路 | 三项健康后绿常亮 | NET语义是整体网络，而不是只判断网线 |
| 所有允许使用的网络均确认不可用 | 红常亮 | 网络down优先，即使同时MQTT/GPS/TK8710异常也先显示红常亮 |
| 重新插网线，carrier恢复但尚未通过IP及连通性检测 | 绿闪或保留已锁存的红闪 | 不能立即绿常亮；失效前的up结果不复用 |
| 网络已恢复，MQTT或网关尚未就绪 | 准备阶段绿闪，或已有业务故障时继续红闪 | 只有三项都健康才可恢复绿常亮 |
| 网络状态文件过期/身份不符，无法确定是否真断网 | 宽限内绿闪；已正常运行或超出宽限后红闪 | 不把“监测失效”错误显示成“已确认断网”的红常亮 |
| 正常发起扫频 | 绿闪；恢复业务且三项健康后绿常亮 | 扫频暂停正常业务，当前灯控显示预算600秒，不会因此主动终止扫频 |
| 扫频后恢复业务失败 | 红闪 | scan_restore_failed等故障被锁存 |
| TK8710/MQTT退出、僵尸或PID被复用 | 旧快照不能维持绿常亮 | 曾经READY后必要快照缺失即红闪；首次启动按宽限规则处理 |
| TK8710反复启动 | 观测到300秒内3次启动身份变化后红闪锁存 | LED侧采样计数，并非完整退出审计；未采到的短命进程不保证计数完整 |
| 业务故障已经恢复 | 继续红闪，三项健康连续30秒后绿常亮 | 防止异常进程短暂启动就闪回绿色 |
| 正常升级维护标志存在 | 绿闪；若同时明确全网down仍红常亮 | 当前灯控连续观察维护最多600秒，超时转业务故障处理 |
| led_agent异常退出 | 短暂失去灯光保证→监护拉起→按最新状态显示 | 监护约1秒检查，重试间隔至少5秒；实板强杀后约1.328秒拉起。恢复时不保证一上来就是绿常亮 |
| 执行S37led_agent stop | 关闭两路后释放GPIO，保持停止 | 无自动拉起；释放后的实际电平由硬件决定，不再代表业务状态 |
| 执行单灯/闪灯测试 | 按测试脚本显示 | 此时颜色不代表业务健康；暂停租约内不抢GPIO，结束后恢复仲裁 |

### 2.2 常见组合与现场判断

| 同时发生的状态 | 最终显示 |
|---|---|
| 无可用网络 + GPS模块缺失 | 红常亮（可信网络down优先） |
| 网络正常 + GPS必须开启但模块缺失 | 捕获故障或满足失效/重启判定后红闪 |
| 网络正常 + MQTT正常 + 正在等待GPS | 没有已锁存故障时绿闪 |
| 网络正常 + GPS关闭 + 本地同步业务就绪 + MQTT正常 | 健康稳定后绿常亮 |
| 网络正常 + 网关就绪 + MQTT订阅失败 | 红闪 |
| 网络恢复 + 先前业务故障尚未解除 | 红闪，不能仅因网络恢复变为绿常亮 |

故障进程可能快速退出，消费者先发现“PID已消失”而不是读到fault。尤其初次启动、GPS模块不存在时，红闪时刻可能取决于缺失宽限或重启计数，不能承诺第一次通信失败瞬间就显示红闪。
红常亮只在网络down快照可信且新鲜时有效。如果网络守护随后也失去更新，网络状态变成未知/过期，灯可能改为红闪；这表示监测依据失效，不表示网络已经恢复。
正常软件仲裁不会主动显示混合色；若长期看见红绿同时亮，应检查是否运行手工测试、旧程序或外接灯接线/驱动电路。

## 3. 仲裁优先级

依次判断，命中即停止：

1. 明确无可用网络（可信且新鲜的network=down）→ 红常亮。
2. 有效升级维护标志且当前灯控连续观察未超过600秒 → 绿慢闪。
3. 任一可信业务故障，或必要状态缺失/过期超过宽限、阶段超时、反复重启 → 按类别红单/双/三/四闪并锁存；三项健康连续30秒后解除。类别优先级：明确HAL/RF/TRM > GPS > MQTT > NS配置 > 通用监测异常。
4. 已锁存故障尚未满足解除条件 → 保留对应红色分组灯语，不因重新进入准备阶段改为绿闪；只允许更高优先级明确故障升级类别。
5. 网络/MQTT准备、HAL配置→绿单闪；等待NS→绿双闪；等待GPS/PPS→绿三闪；扫频→绿均匀慢闪。
6. 网络up、MQTTconnected、网关running且business_ready=true全部满足 → 健康稳定3秒后绿常亮；已有故障锁存时按30秒恢复规则。

运行故障从READY转BUSINESS_FAULT时不再享受开机宽限；正常开机给予一次启动预算。网络up恢复后仍需检查业务，不能直接把红灯变成绿常亮。
MQTT/网关进程不存在时，其旧状态文件只用于错误诊断，不能作为当前健康依据。
网络查询本身失败或状态过期属于“监测不可用”，不能伪装成已确认断网；宽限后通用红四闪（不覆盖已有更高优先级故障），具体原因查看网络JSON与LED日志。

## 4. 状态来源与职责

| 生产者 | 职责 | 消费者 |
|---|---|---|
| 网络守护 | 链路、IP、连通性、切换状态及检测进度 | LED/Web |
| mqtt_bridge | broker连接成功/失败/断开、订阅结果、重连进度 | LED/Web |
| tk8710_gw | NS配置、GPS/PPS准备、HAL启动、运行/扫频/异常/退出 | LED/Web/MQTT可读 |
| led_agent | 校验输入、仲裁整机状态、独占两路GPIO | 对外指示灯 |

不要让MQTT和网关程序直接操作灯GPIO。不要通过解析日志推断状态。led_agent自身存活并不代表网络或业务健康。

## 5. TK8710生命周期接口（本次已实现）

文件：`/var/run/tk8710_gw/status.json`，通常对应tmpfs `/run/tk8710_gw/status.json`。
同目录已有`version.txt`保持原格式；`/var/run/tk8710_gps_policy`、GPSinfo.txt、RFstatus.txt的协议也保持不变。
新状态文件固定路径不随`-w`切换，便于其它应用统一读取。

示例（字段值仅作说明）：

```json
{
  "schema": 1,
  "pid": 1234,
  "start_ticks": 900,
  "boot_id": "01234567-89ab-cdef-0123-456789abcdef",
  "state": "wait_gps_sync",
  "reason": "gps_acquisition",
  "error_code": 0,
  "gps_enable": 1,
  "business_ready": false,
  "exited": false,
  "state_since_mono_ms": 15000,
  "updated_mono_ms": 16000,
  "phase_timeout_s": 330
}
```

PID及start_ticks仅供本地身份校验，不新增到NS上行报文。两个时间字段来自CLOCK_MONOTONIC，单位毫秒，不能与date或NTP时间相减。start_ticks是/proc进程启动字段，不能当成毫秒。

| state | 设置位置/条件 | business_ready | 建议灯语 |
|---|---|---|---|
| starting | 运行目录准备后，RF校准读取及CPU绑定等启动准备 | false | 绿闪 |
| wait_ns_config | IPC线程启动前，等待显式NS配置 | false | 绿闪 |
| configuring | 收到配置、HAL初始化/配置、扫频后恢复 | false | 绿闪 |
| wait_gps_sync | NS要求GPS，模块探测和基础GPS/PPS健康获取中 | false | 绿闪 |
| wait_pps_alignment | 下发OUT ON/SET PERIOD并等待输出同步达标 | false | 绿闪 |
| running | 配置回调成功且HAL启动完成，或运行健康检查通过 | true | 还需网络/MQTT就绪才能绿常亮 |
| degraded | GPS检查出现异常/输出PPS缺失，或检测到少量异常RF通道 | false | 红闪（灯侧可做短时去抖） |
| scanning | 托管扫频启动，正常业务暂不可用 | false | 绿闪 |
| stopping | 正常退出、恢复后请求重启，正在清理 | false | 绿闪，超时后红闪 |
| stopped | 正常清理结束 | false | 按维护标志/重启宽限处理，不能绿常亮 |
| fault | 显式致命错误 | false | 网络可用时红闪 |

GPS开关为0时跳过两个GPS等待阶段，正常本地同步仍可进入running。开关为1但模块缺失或不健康时仍按现有策略拒绝启动；不会为灯语而回退本地同步。
运行中的GPS异常、RF异常灯语是观察结果；原有连续失败阈值和退出策略不由状态发布模块改变。
running不是MQTT连接声明，不保证每根天线正常，也不代表已完成射频端到端验收；首次启动至下一次约10秒健康采样之间可能尚未暴露硬件异常。

### 5.1 错误原因

主要reason：ns_config_timeout、invalid_gps_policy、gps_module_unavailable、gps_sync_failed、pps_alignment_failed、pps_period_invalid、hal_init_failed、hal_start_failed、pps_monitor_failed、ns_config_failed、ns_config_apply_timeout、scan_restore_failed、gps_runtime_failed、rf_channels_failed、trm_shutdown_requested、console_or_irq_watchdog_failed、capture_config_failed。
通用配置失败保留具体阶段先记录的故障；首次fault锁存，迟到的成功回调或退出清理不能覆盖为running/stopped。
正常终止不伪造初始化失败；显式错误结束仍保留fault并设置exited=true。

### 5.2 发布与失效规则

- 状态切换立即发布；main等待循环调用Touch，每秒最多刷新一次。正常业务主循环受现有10秒控制台/健康轮询影响，通常约10秒更新一次，**不是固定1秒心跳**。
- 独立线程不虚构“业务存活心跳”。updated_mono_ms代表发布/主流程检查点，不证明RF收发成功；判断卡住还需阶段预算或运行期新鲜度。
- GPS等待由IPC线程执行；启动等待和重新配置期间main的Touch继续刷新，但state_since_mono_ms不变，因此卡在同阶段仍能被阶段预算识别。
- 用同目录临时文件+rename，互斥锁保护多线程写入。消费者只读status.json，忽略.tmp。
- 发布失败告警，不改变网关业务流程；消费者必须识别缺失/旧状态。status.lock仅避免两个进程争写状态文件，不代替现有业务进程单实例管理。
- SIGKILL/崩溃无法写最后状态：消费者核对boot_id、pid、start_ticks、进程身份及是否僵尸；旧文件不能显示正常。正常退出保留最终状态供排查，下一次启动覆盖。
- 写入init成功不等于已业务就绪，消费者只信经过身份校验的有效快照。

## 6. 时间参数（灯控实施建议）

| 场景 | 当前业务事实/建议 |
|---|---|
| LED轮询 | 分组版实际50ms，闪烁按单调时间计算，模式变化从第一下开始 |
| 物理断线检测 | 建议独立1秒检查或netlink通知；不等待慢Ping完成 |
| 网络L3检测 | 原周期10、每目标5包；建议快检测与质量统计分离，联网判断总预算明确限制 |
| 网络状态发布 | 建议每1秒刷新发布者存活时间，结果时间单独记录；禁止把正在探测当成up |
| MQTT连接宽限 | 首次连接/断线后最多10秒绿闪；超时红闪；需与实际重连策略一起验收 |
| 进程首次启动宽限 | 建议跟随tdaemon发布的业务启动时间，30秒；不能从Linux开机算，因为网络准备可能较长 |
| NS等待 | 当前最多3次、每次约10秒；程序无配置后fault退出。消费者显示预算35秒 |
| GPS基础获取 | 当前搜索300秒，另有模块探测/诊断耗时；显示预算330秒 |
| PPS对齐 | 当前对齐60秒，另有UART命令/诊断耗时；显示预算90秒 |
| HAL configuring | 显示预算120秒；当前整个配置应用等待上限420秒优先，以显式fault为准 |
| starting / stopping | 显示预算60秒 / 30秒 |
| running / degraded快照 | 建议超过45秒无检查点视为过期，保留诊断，不显示绿常亮 |
| 扫频 | 当前phase_timeout_s=0，不据此判定无限成功；后续需由扫频管理器提供任务deadline，独立检查快照新鲜度 |
| 恢复绿常亮 | 建议健康条件连续保持3秒后恢复，减少抖动；显式fault立即红闪 |
| 反复重启 | 建议300秒内3次异常退出则红闪锁存；连续健康30秒解除，正常升级维护不计入 |

所有phase_timeout_s均是状态消费者的显示预算，未新增/改变网关业务超时。需要实际冷启动和极端负载数据校准。
重启次数应由tdaemon记录，LED进程重启不应把故障历史清空；建议存在/run/led的独立记录，整机重启清零。不得以“每次进程重启都重新绿闪等待”掩盖启动循环失败。

## 7. MQTT与网络接口改造（已实现状态生产者）

保留现有mqtt.state/net.state以兼容旧灯控，另发布schema=1的新快照，如`/run/led/mqtt_status.json`与`network_status.json`。新LED只使用新协议，不把旧connected当真。

实现补充：网络shell使用/proc/uptime即CLOCK_BOOTTIME，字段为updated_boottime_ms、checked_boottime_ms；MQTT使用CLOCK_MONOTONIC。消费者须按clock选择时间基准。原方案中笼统的网络*_mono_ms命名以配套接口说明为准。

MQTT状态：connecting、connected、reconnecting、fault、stopped。connected必须来自成功CONNACK且下行订阅得到成功确认；断开回调立即取消。主循环只刷新存活字段，不再无条件刷新connected。消息publish进入发送队列不代表NS已接收。
网络状态：unknown、checking、up、switching、down，附active_iface、allowed_ifaces、reason、updated_mono_ms、checked_mono_ms、publisher身份。carrier、IPv4、目标可达性要分开记录。
ETH断开后其他已验证链路仍正常，保持up；备用网络未验证则switching；全部检查失败才down。长恢复操作期间旧结果不能无限保鲜，超时转unknown/监测故障。
维护升级期间使用现有`/var/run/app-upgrade-maintenance`，由独立维护状态及最长预算支持绿闪，不屏蔽真实网络全断，也不能无限掩盖维护卡死。
