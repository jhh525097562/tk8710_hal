这个需求非常适合做成“**一个灯看健康，一个灯看业务**”，我建议用最简方案（看一眼能懂）：

**推荐灯语（简洁版）**
- **运行灯（RUN）**
  - 常亮：系统正常运行，无明显数据流
  - 快闪（5Hz，100ms亮/100ms灭）：有数据
- **网络灯（NET）**
  - 灭：无 L3（无 IP 或 ping 不通）
  - 常亮：L3 正常（当前链路可达目标）
  - 快闪（2Hz）：正在切换链路或执行恢复动作

**为什么这样分**

- RUN 负责“设备活着没、有没有业务流量”
- NET 负责“链路是否真通公网（L3）”
- 两灯组合可快速判断：
  - RUN常亮 + NET常亮：健康
  - RUN快闪 + NET常亮：业务活跃
  - RUN常亮 + NET灭：系统活着但断网
  - RUN常亮 + NET快闪：正在自恢复链路

**实现建议（避免花屏）**

- 状态刷新周期 200ms
- 最短状态保持 1s（防止频繁抖动）
- 数据流触发用“窗口计数”（如最近1秒有包就显示快闪）



这个场景我建议**不要分散在各进程里直接控灯**，最佳是“**单独一个 LED Agent 进程**”，其他进程只上报状态。

**为什么**
- 两个灯都要表达“跨进程状态”（MQTT + 网络守护），如果各自直接 `gpioset` 会抢占、打架、闪烁混乱。
- 灯语优先级需要统一仲裁（例如“网络恢复中”是否覆盖“有上行”）。
- 后续你加状态（升级、故障码）时，集中式最容易扩展。

**推荐架构（简洁可落地）**
- **MQTT进程**：只输出状态到 `/run/led/mqtt.state`（connected/up/down/ 时间戳）
- **网络守护脚本**：只输出状态到 `/run/led/net.state`（L3 ok/switching/recovering/current iface）
- **LED Agent（单独程序）**：唯一操控 GPIO，按状态机驱动 RUN/NET 两灯

**三种方案对比**
- **方案A：都放各自进程里控灯**  
  - 优点：改动少  
  - 缺点：冲突高，不建议
- **方案B：单独 LED Agent（推荐）**  
  - 优点：职责清晰、稳定、可维护  
  - 缺点：多一个常驻脚本
- **方案C：网络守护统一控灯**  
  - 优点：少一个进程  
  - 缺点：MQTT业务语义会耦合进网络脚本，后期会臃肿

**建议结论**
- 采用 **方案B**：`S37led_agent`（SysV），持续轮询状态文件并控灯。
- 约束：**只有 LED Agent 能调用 gpioset**，其他进程严禁直接碰 LED 引脚。
