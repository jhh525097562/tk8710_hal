# 分组双色灯语（2026-10-09）

本版本替代原来“绿/红各一种慢闪”的灯语；GPIO、有效电平和LED自动拉起机制不变。

| 灯型 | 日志mode | 含义 |
|---|---|---|
| 绿常亮 | ready | 网络、MQTT、TK8710全部就绪 |
| 绿单闪 | green_single | 启动、联网/MQTT准备、HAL配置 |
| 绿双闪 | green_double | 等待NS配置 |
| 绿三闪 | green_triple | 等待GPS基础同步或PPS对齐 |
| 绿均匀慢闪 | green_slow | 扫频或有时限维护 |
| 红常亮 | network_fault | 可信且新鲜的网络down |
| 红单闪 | red_single | MQTT连接、认证、订阅故障或等待超时 |
| 红双闪 | red_double | NS配置超时/无效，包括invalid_gps_policy |
| 红三闪 | red_triple | GPS模块缺失、GPS/PPS同步失败或运行健康异常 |
| 红四闪 | red_four | 明确HAL/RF/TRM故障，或无法归因的进程/监测异常 |

短闪亮250ms，组内灭250ms；最后一下熄灭至下一组开始为2000ms。单/双/三/四闪的组周期分别2250、2750、3250、3750ms。
均匀慢闪亮1秒/灭1秒。模式变化从第一下重新开始；同模式快照更新不重置计数。生产程序50ms轮询，存在GPIO/调度延迟，不是硬实时输出。

## 分类与锁存

保留原JSON身份、新鲜度、阶段超时检查。wait_ns_config为绿双闪；wait_gps_sync/wait_pps_alignment为绿三闪；scanning为绿均匀慢闪。
故障reason中gps_*/pps_*为红三闪；ns_config*、invalid_gps_policy为红双闪；hal_*/rf_*/trm_*、console_or_irq*、scan_restore_failed为明确网关故障红四闪。其它缺失/过期/未知故障是低优先级通用红四闪。

网络down优先，有效维护按原规则绿均匀慢闪。业务原因优先级：明确HAL/RF/TRM > GPS > MQTT > NS配置 > 未归因监测异常。
只显示一个主要故障，不轮播。保留已锁存原因中优先级最高者，直到全部健康连续30秒；普通进程消失或重新等待不能将已知GPS红三闪覆盖成红四闪/绿三闪。初次健康仍稳定3秒后绿常亮。
已知故障已恢复但整体未恢复时，仍可能显示其锁存类别；当前模块详情应看JSON/日志。

`/run/led/arbiter_history`增加fault_class尾字段：0无、1通用、2配置、3MQTT、4GPS、5硬件。兼容旧6字段文件；旧锁存无类别按通用红四闪。同boot_id下才恢复历史。
已退出进程仅允许保留与先前观察到的网关start_ticks及当前boot_id一致、尚未过期的fault，绝不使用死进程ready。若进程从启动到退出都太快、未观察到身份，仍可能只能显示通用红四闪。

## 验证与回退

- `test_unified_led.py`：18项ARM/QEMU测试，包括全部分组脉冲数、2秒组间停顿、两极性互斥、原因优先级、锁存及解析。
- `tests/led_pattern_test.c`：使用生产LedLevels实现，输出10种灯型并读回GPIO。
- `tests/run_grouped_board.sh`：申请120秒监护暂停租约，测试结束恢复；不修改业务快照，不制造断网或GPS故障。
- 本地旧版备份：`backup/before_grouped_20261009_104648/`。
- 板端证据：`logs/led_grouped_20261009_105021/`；旧程序：`/userdata/led_grouped_20261009_105021/led_agent.old`。

GPIO读回和时间戳验证软件输出，不代替现场颜色观感或示波器测量；真实GPS缺失、断网、broker拒绝等故障链路仍需分别实板验收。

192.168.100.202本轮实测通过：10种灯型均输出并读回，7种分组灯型各运行2组，脉冲数分别符合单/双/三/四闪。短亮时间242～255ms；均匀慢闪亮灯999～1003ms。各采样未出现两路同时为高。
测试返回0后安装新版，监护自动恢复LED；正常状态先green_single，约3秒后ready。最终GPIO1_C7高、GPIO1_D0低，业务进程MQTT3941、TK87101643、rk_wdt651与测试前相同。
本地、SDK源码与rootfs预置程序已同步；完整升级包未重制，未上传Git。
