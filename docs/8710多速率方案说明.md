# 8710多速率方案说明

## 1. 文档目的

本文档用于说明 TK8710 在多速率场景下的实现方案、已知问题、规避思路以及终端侧配合方式。

当前版本先聚焦以下内容：

- 说明 TK8710 的基本帧结构和时隙循环方式。
- 说明直接做“逐帧切换速率”时出现的问题。
- 说明当前可落地的两速率多速率方案。
- 说明终端如何基于该方案完成同步、入网和数据收发。

多速率配置限制项后续补充。

## 2. TK8710基础时隙结构

根据 TK8710 手册，8710 的一个完整 frame 最多包含 4 个 slot，按顺序循环工作。本文讨论的网关工作方式采用固定 4 时隙结构：

- `slot0`：`BCN`
- `slot1`：`Tx`
- `slot2`：`Rx`
- `slot3`：`Tx`

也可以写成：

`BCN + Tx + Rx + Tx`

其中：

- `slot0 + slot1 + slot2 + slot3` 构成 `1帧`
- 4 个时隙按固定顺序持续循环运行
- 8710 支持在 `slot3` 结束中断中配置“下一帧”的工作参数

## 3. 多速率的原始思路

原始思路是：利用 8710 支持在 `slot3` 中断中切换下一帧参数的能力，在每一帧结束时切换下一帧的速率模式。

例如：

- 当前帧工作在 `mode5`
- 在当前帧的 `slot3` 中断中，将下一帧切换到 `mode6`

从功能预期上看，这样可以实现：

- 第 N 帧使用一种速率
- 第 N+1 帧切换到另一种速率
- 多个速率按帧粒度轮流工作

## 4. 原始思路存在的问题

实际验证发现，8710 虽然支持在 `slot3` 中断中切换下一帧速率模式，但芯片设计时并未完整考虑这种“多速率逐帧切换”的使用方式。

具体表现为：

- 在 `slot3` 中断中切换到下一帧速率后，`slot0` 所使用的 `BCN` 调制相关序列没有同步更新
- 因此，切换速率后的 `slot0` 虽然仍然存在，但 `BCN` 发送会异常
- 在未切换速率之前，`BCN` 发送是正常的
- 速率切换后的 `Tx` 和 `Rx` 仍然可以正常工作

也就是说，问题集中在：

- `slot0` 的 `BCN`
- 尤其是 `BCN` 调制所依赖的序列未随速率切换而更新

因此，不能直接把“每一帧都按当前速率正常发 BCN”作为多速率方案来使用。

## 5. 当前可用的多速率方案

### 5.1 方案核心思路

既然切换后“数据时隙可正常工作、但切换速率后的 BCN 异常”，那么规避思路就是：

- 只让一个基准速率负责正常发送 BCN
- 其它速率帧仍然保留 `slot0` 时隙位置，但不实际发射 BCN 信号
- 利用非基准速率帧的 `Tx/Rx` 时隙承载业务数据

这样可以绕开“切换速率后 BCN 序列未更新”的问题，同时保留多速率业务传输能力。

### 5.2 两速率示例

以两个速率为例：

- 第一个速率：`mode5`
- 第二个速率：`mode6`

两种速率都各自对应完整的 4 时隙帧：

- `mode5`：`slot0 + slot1 + slot2 + slot3`
- `mode6`：`slot0 + slot1 + slot2 + slot3`

### 5.3 运行流程

#### 帧A：mode5帧

`mode5` 作为基准速率帧，正常发送 `BCN`。

其工作方式为：

- `slot0`：正常发送 `mode5` 的 `BCN`
- `slot1`：按 `mode5` 配置发送数据
- `slot2`：按 `mode5` 配置接收数据
- `slot3`：按 `mode5` 配置发送数据

在 `mode5` 的 `slot3` 中断中，执行两项操作：

- 将下一帧速率切换为 `mode6`
- 将 `bcn` 发送使能关闭

关闭 `bcn` 发送使能后，下一帧中的 `slot0` 仍然存在，但射频不发送 `BCN` 信号。

#### 帧B：mode6帧

`mode6` 帧的作用是承载 `mode6` 下的业务数据，而不负责正常广播 `BCN`。

其工作方式为：

- `slot0`：时隙仍然存在，但不发射 `BCN`
- `slot1`：按 `mode6` 配置发送数据
- `slot2`：按 `mode6` 配置接收数据
- `slot3`：按 `mode6` 配置发送数据

在 `mode6` 的 `slot3` 中断中，执行两项操作：

- 将下一帧速率切换回 `mode5`
- 将 `bcn` 发送使能打开

这样，回到下一帧 `mode5` 时，又能正常发送 `mode5` 的 `BCN`。

### 5.4 周期性循环

上述两帧会持续循环：

1. `mode5` 帧正常发 `BCN`，并承载 `mode5` 数据收发
2. 切到 `mode6` 帧，关闭 `BCN` 发射，仅承载 `mode6` 数据收发
3. 再切回 `mode5` 帧，恢复 `BCN` 发射
4. 重复循环

因此，从空口表现上看：

- `mode5` 是对外广播同步基准速率
- `mode6` 是插入在循环中的辅助业务速率

## 6. 该方案的关键特点

该方案的本质不是“所有速率都各自正常发送 BCN”，而是：

- 只有第一个低速率负责稳定发送 `BCN`
- 其它高速率只负责业务时隙收发
- 非基准速率帧的 `slot0` 保留时序位置，但不实际发送 `BCN`

这样做有几个直接结果：

- 终端的同步基准始终统一，不会因为多速率切换而失去基准
- 可以避免切换速率后 `BCN` 异常的问题
- 多速率能力仍然可以通过不同帧中的 `Tx/Rx` 时隙体现出来

## 7. 终端侧配合方式

### 7.1 终端同步基准

终端侧按照最低速率接收 8710 发送的 `BCN`。

在上述两速率示例中：

- 终端始终接收第一个速率的 `BCN`
- 即始终接收 `mode5` 的 `BCN`
- 并以该 `BCN` 作为时隙同步基准

终端不依赖 `mode6` 帧的 `slot0` 来做同步，因为该时隙虽然存在，但不发送 `BCN`。

### 7.2 终端获取多速率配置信息

终端通过 8710 的第一个 `Tx` 时隙内容，获取当前网关支持的多速率信息。

这里约定：

- 第一个 `Tx` 的长度固定
- 第一个 `Tx` 中携带多速率描述信息

终端需要从该固定长度内容中获取至少以下信息：

- 当前 8710 支持几种速率
- 每种速率对应的各个 `slot` 长度

必要时，也可以继续扩展携带其它多速率相关参数。

### 7.3 终端保持时隙对齐

终端先通过第一个速率的 `BCN` 建立同步，再结合第一个 `Tx` 中携带的多速率时隙信息，保持与网关的时隙对齐关系。

终端侧的基本原则是：

- 始终跟随网关第一个速率的 `BCN`
- 始终以该 `BCN` 维持帧边界对齐
- 在已知多速率时隙长度配置的前提下，推导其它速率帧中的业务时隙位置

也就是说，终端虽然只接收第一个速率的 `BCN`，但仍然可以知道后续其它速率帧里的业务时隙何时到来。

## 8. 终端业务工作方式

在完成同步并获取多速率配置后，终端可以按以下方式工作：

- 在设定的目标速率上进行入网
- 在设定的目标速率上进行上下行数据收发
- 或者启用终端自适应速率控制

### 8.1 固定速率工作

若终端被配置为固定工作在某个速率，则：

- 同步仍然依赖第一个速率的 `BCN`
- 业务收发在目标速率对应的业务时隙中进行

### 8.2 自适应速率工作

终端也可以根据接收到的第一个速率 `BCN` 的信号强度，自动调整自己的工作速率。

即：

- 终端持续测量第一个速率 `BCN` 的信号强度
- 根据预设门限或策略，选择更合适的工作速率
- 然后在所选速率对应的业务时隙上完成入网和数据收发

这种方式下：

- `BCN` 只承担同步和速率判断参考作用
- 实际业务收发可在其它配置速率上进行

## 9. 方案总结

8710 的多速率方案需要建立在一个前提上：8710 虽然支持在 `slot3` 中断中切换下一帧速率，但切换后无法保证下一帧 `slot0` 的 `BCN` 调制序列正确更新，因此不能直接实现“每个速率帧都正常发 BCN”的设计。

当前可行方案是：

- 选择第一个速率作为基准速率
- 仅由第一个速率正常发送 `BCN`
- 在其它速率帧中保留 `slot0` 时隙但关闭 `BCN` 发射
- 通过第一个 `Tx` 向终端告知多速率配置
- 终端始终跟随第一个速率 `BCN` 进行同步，并在目标速率对应时隙中完成业务收发

以两速率为例，就是：

- `mode5` 帧：发 `BCN`，并进行 `mode5` 数据收发
- `mode6` 帧：不发 `BCN`，只进行 `mode6` 数据收发
- 两种帧在 `slot3` 中断中相互切换，循环运行

## 10. 多速率配置限制初步设计

本章节基于你补充的同步精度和抗时偏能力，给出一个初步的多速率组合设计结论。

当前只考虑：

- `BCN` 时间同步精度
- `data` 抗时偏能力

当前暂不考虑：

- `data` 抗频偏能力

### 10.1 已知条件

#### BCN 速率范围

- `BCN` 可从 `mode5`、`mode6`、`mode7`、`mode8` 开始
- 当 `BCN` 到 `mode9` 后，后续保持 `mode9`
- 后续 `data` 速率模式可为 `mode9`、`mode10`、`mode11`、`mode18`

#### BCN 时间同步精度

| BCN模式 | 时间同步精度 | 频率同步精度 |
| --- | --- | --- |
| mode5 | 0.256 ms | 15.26 Hz |
| mode6 | 0.128 ms | 30.52 Hz |
| mode7 | 0.064 ms | 61.04 Hz |
| mode8 | 0.032 ms | 122.07 Hz |
| mode9 | 0.032 ms | 244.14 Hz |

#### BCN 最大同步时偏

按你的约束：

`BCN最大同步时偏 = 2 × BCN时间同步精度`

因此可得：

| BCN模式 | 时间同步精度 | 最大同步时偏 |
| --- | --- | --- |
| mode5 | 0.256 ms | 0.512 ms |
| mode6 | 0.128 ms | 0.256 ms |
| mode7 | 0.064 ms | 0.128 ms |
| mode8 | 0.032 ms | 0.064 ms |
| mode9 | 0.032 ms | 0.064 ms |

#### Data 抗时偏能力

| Data模式 | 抗时偏能力 |
| --- | --- |
| mode5 | 4 ms |
| mode6 | 4 ms |
| mode7 | 4 ms |
| mode8 | 4 ms |
| mode9 | 1 ms |
| mode10 | 0.5 ms |
| mode11 | 0.25 ms |
| mode18 | 0.25 ms |

### 10.2 判定原则

采用以下保守判据：

`若 BCN最大同步时偏 <= Data抗时偏能力，则认为该最低速率可以支持该Data速率。`

说明：

- 这里的“最低速率”本质上是终端用于同步基准的最低 `BCN` 速率
- 因为终端始终依赖最低速率 `BCN` 建立和维持时隙对齐
- 所以是否能支持更高速率，主要取决于该 `BCN` 基准带来的最坏同步时偏，是否落在目标 `data` 模式可容忍范围内

### 10.3 各最低速率对应的最大支持速率

#### 最低速率为 mode5

- `BCN` 最大同步时偏：`0.512 ms`
- 可支持的 `data` 模式：`mode5`、`mode6`、`mode7`、`mode8`、`mode9`
- 不支持的更高速率：`mode10`、`mode11`、`mode18`

原因：

- `mode9` 抗时偏能力为 `1 ms`，大于 `0.512 ms`，可支持
- `mode10` 抗时偏能力为 `0.5 ms`，小于 `0.512 ms`，不可支持
- `mode11`、`mode18` 抗时偏能力均为 `0.25 ms`，不可支持

结论：

- `mode5` 作为最低速率时，最大支持到 `mode9`
- 不能稳定支持到 `mode18`

#### 最低速率为 mode6

- `BCN` 最大同步时偏：`0.256 ms`
- 可支持的 `data` 模式：`mode6`、`mode7`、`mode8`、`mode9`、`mode10`
- 不支持的更高速率：`mode11`、`mode18`

原因：

- `mode10` 抗时偏能力为 `0.5 ms`，大于 `0.256 ms`，可支持
- `mode11`、`mode18` 抗时偏能力均为 `0.25 ms`，略小于 `0.256 ms`，按保守设计不可支持

结论：

- `mode6` 作为最低速率时，最大支持到 `mode10`

#### 最低速率为 mode7

- `BCN` 最大同步时偏：`0.128 ms`
- 可支持的 `data` 模式：`mode7`、`mode8`、`mode9`、`mode10`、`mode11`、`mode18`

原因：

- `mode11`、`mode18` 抗时偏能力均为 `0.25 ms`
- `0.128 ms < 0.25 ms`

结论：

- `mode7` 作为最低速率时，最大支持到 `mode18`

#### 最低速率为 mode8

- `BCN` 最大同步时偏：`0.064 ms`
- 可支持的 `data` 模式：`mode8`、`mode9`、`mode10`、`mode11`、`mode18`

结论：

- `mode8` 作为最低速率时，最大支持到 `mode18`

#### 最低速率为 mode9

- `BCN` 最大同步时偏：`0.064 ms`
- 可支持的 `data` 模式：`mode9`、`mode10`、`mode11`、`mode18`

结论：

- `mode9` 作为最低速率时，最大支持到 `mode18`

### 10.4 汇总结论表

| 最低速率（同步基准BCN） | BCN最大同步时偏 | 可支持的Data速率 | 最大支持速率 |
| --- | --- | --- | --- |
| mode5 | 0.512 ms | mode5、mode6、mode7、mode8、mode9 | mode9 |
| mode6 | 0.256 ms | mode6、mode7、mode8、mode9、mode10 | mode10 |
| mode7 | 0.128 ms | mode7、mode8、mode9、mode10、mode11、mode18 | mode18 |
| mode8 | 0.064 ms | mode8、mode9、mode10、mode11、mode18 | mode18 |
| mode9 | 0.064 ms | mode9、mode10、mode11、mode18 | mode18 |

### 10.5 设计建议

基于当前时偏约束，建议按以下方式设计：

- 若系统最低速率选 `mode5`，则高速率上限建议限制在 `mode9`
- 若系统最低速率选 `mode6`，则高速率上限建议限制在 `mode10`
- 若系统希望支持到 `mode11` 或 `mode18`，则最低速率建议至少为 `mode7`

换句话说：

- `mode5 -> mode18`：不建议，不满足保守时偏约束
- `mode6 -> mode18`：不建议，不满足保守时偏约束
- `mode7 -> mode18`：可以作为可行方案
- `mode8 -> mode18`：可以作为可行方案
- `mode9 -> mode18`：可以作为可行方案

需要特别说明的是：

- `mode5 -> mode10` 并不一定表现为“完全不可通信”
- 但由于其时偏容限已经小于最低速率 `mode5` 的最坏同步时偏上界，因此属于边界不稳定组合
- 这类组合即使在部分场景下可以收发，也不适合作为稳定配置推荐

### 10.6 实测结果补充

已有一组实测结果可用于和上述理论判断进行对照。

#### 测试条件

- 最低速率：`mode5`
- 配置速率结构：`mode5`、`mode9`、`mode10`、`mode11`
- 测试对象：4 种速率上的工作稳定性
- 信道条件：`SNR` 在 `10` 附近
- 测试方式：每种速率测试 `20` 包数据
- 业务特征：带 `ACK` 确认包

#### 测试结果

| 速率 | 丢包率 | 对应丢包包数（20包） |
| --- | --- | --- |
| mode5 | 0% | 0 |
| mode9 | 0% | 0 |
| mode10 | 10% | 2 |
| mode11 | 50% | 10 |

#### 实测结果分析

这组结果与前述按时偏能力得到的保守结论是基本一致的。

1. `mode5`

- 丢包率 `0%`
- 说明最低速率本身工作稳定

2. `mode9`

- 丢包率 `0%`
- 说明 `mode5` 作为同步基准时，支撑到 `mode9` 是稳定可行的

3. `mode10`

- 丢包率 `10%`
- 说明 `mode10` 已经进入边界工作区
- 即使在 `SNR` 约 `10` 的条件下，也只能做到“基本可通信，但稳定性不足”

4. `mode11`

- 丢包率 `50%`
- 说明 `mode11` 明显超出了 `mode5` 基准下可稳定支撑的范围

#### 实测结论

对于“最低速率为 `mode5`”的多速率配置，当前可以得出更贴近工程使用的结论：

- `mode5`
  稳定
- `mode9`
  稳定
- `mode10`
  可通信，但不稳定，不建议作为正式配置
- `mode11`
  明显不稳定，不建议配置

因此，从工程推荐角度看：

- `mode5` 作为最低速率时，稳定支持上限仍建议定义为 `mode9`
- `mode10` 可以视为“临界可用但不推荐”
- `mode11` 及更高模式在该基准下不建议使用
