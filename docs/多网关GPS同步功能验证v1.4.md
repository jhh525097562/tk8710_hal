# 多网关 GPS 同步功能验证

**版本：** V1.4
**更新日期：** 2026-09-11
**被测程序：** `test/example/tk8710_gw.c`

## 1. 验证目的

本文用于验证 RK3506 网关对 GPS/PPS 模块的自动识别、启动降级和外部同步功能，并进一步验证多台同频网关在共同 GPS 时间基准下的同步组网能力。

验证范围包括：

1. 单网关、无 GPS 模块时自动选择本地同步并启动。
2. 单网关、有 GPS 模块但无有效 PPS 信号时的等待、超时和降级启动。
3. 单网关、有 GPS 模块且 GPS/PPS 正常时的外部同步启动。
4. 两台 GPS 网关在无超帧配置下的同频同步和终端移动测试（两台网关发送不同bcnbits、终端加60dB固定衰减、从一台网关靠近另一台网关，查看终端接收bcnbits结果、两台网关上行/下行数据接收情况）。
5. 两台 GPS 网关在 20 帧超帧配置下的同频同步和终端移动测试（两台网关发送不同bcnbits、终端加60dB固定衰减、从一台网关靠近另一台网关，查看终端接收bcnbits、TDD序号、两台网关上行/下行数据接收情况）。
6. 两台 GPS 网关在多速率配置下的速率轮转同步和终端移动测试。

本方案验证软件状态、串口状态、TK8710 同步配置和实际收发结果。UART 返回的 `RUNNING/ALIGN=1` 只能证明 GPS/PPS 模块内部状态，不能单独替代两台网关射频时隙边界的物理同步测量。

## 2. 被测功能与判定依据

### 2.1 GPS/PPS 启动状态


| 场景                   | 网关预期行为                                           | 关键日志                                                               |
| ---------------------- | ------------------------------------------------------ | ---------------------------------------------------------------------- |
| 无 GPS 模块            | 两次`GET VERSION` 超时后继续启动，使用本地同步         | `GPS/PPS startup mode: ABSENT`、`TK8710 synchronization source: local` |
| 有模块、无有效 GPS/PPS | 最长等待 300 秒；未就绪则采集诊断并本地降级            | `LOCAL_DEGRADED`、GPS/PPS 诊断、local sync                             |
| 有模块且信号正常       | GPS 基础状态就绪后等待 NS 配置，设置周期并使用外部同步 | `EXTERNAL_READY`、`OUT ON`、`SET PERIOD`、`EXTERNAL_ACTIVE`            |

GPS 基础就绪条件：

```text
GPS=1、PPS=1、FIX=1、RMC=A
```

GPS/PPS 完整健康条件：

```text
STATE=RUNNING、PERIOD=期望周期、OUT=1、PENDING=0、
GPS=1、PPS=1、FIX=1、RMC=A、ALIGN=1、HOLD=0、BAD=0、RESYNC=0
```

### 2.2 TK8710 同步模式


| 同步方式          | `slotCfg.local_sync` | `init12.ls_en` | `init12.ls_master` |
| ----------------- | -------------------: | -------------: | -----------------: |
| 本地同步          |                    1 |              0 |                  1 |
| 外部 GPS/PPS 同步 |                    0 |              1 |                  0 |

### 2.3 NS 参数约定

- `bcnbits` 由 NS 配置的 `nwk_num` 低 5 bit 取得。本测试要求网关 1 配置 `nwk_num=1`，网关 2 配置 `nwk_num=2`。
- “无超帧”定义为 `tdd_num=1`，即每个超帧只有 1 个帧。
- “有超帧（20）”定义为 `tdd_num=20`，即每个超帧包含 20 个帧。
- `tdd_num/superFrameNum` 是业务超帧长度；时隙计算器输出的 `frameCount=N` 是整数秒 PPS 对齐周期内的帧数。算法要求 `N % superFrameNum == 0`，但 `N` 不一定等于 `superFrameNum`。
- 两台网关必须使用相同中心频率、速率模式、上下行包块数、时隙结构和超帧长度；只允许 `nwk_num/bcnbits` 不同。
- GPS/PPS 输出周期由时隙计算器结果确定：

```text
PPS周期(s) = framePeriod(us) × frameCount / 1000000
```

计算结果必须是协议允许的整数秒。两台网关对同一组 NS 时隙参数计算出的周期必须一致。

### 2.4 UTC 周期修改与对齐机制

AG32 使用 GPS 提供的有效 UTC 作为 PPS_OUT 周期对齐基准，不使用 RK3506 或测试
PC 的本地时间。网关根据时隙计算结果发送：

```text
SET PERIOD <周期秒数>
```

设配置周期为 `T` 秒，设备选择的目标对齐 UTC 秒点 `U` 必须满足：

```text
U % T == 0
```

设备会自动选择一个满足该条件的未来 UTC PPS 边沿，并在该边沿完成 CPLD 对齐和
新周期切换。例如 `T=7` 时，只有 UTC 整秒值能被 7 整除的 PPS 边沿才是有效对齐点。
命令返回 `OK PERIOD` 只表示周期配置已受理，不能据此判定新周期已经对齐生效。

周期配置后的典型过程如下：

```text
OUT ON
   │
SET PERIOD T
   │
等待 GPS UTC 满足 U % T == 0 的未来 PPS 边沿
   │
EVENT CPLD_ALIGNED UTC=U PERIOD=T ...
   │
RUNNING、PERIOD=T、PENDING=0、ALIGN=1
```

`EVENT CPLD_ALIGNED` 是实际完成 UTC 对齐的直接事件证据。其中 `UTC` 是实际对齐
秒点，`PERIOD` 是已经生效的输出周期。验证时应保存完整事件行，并检查事件中的
`PERIOD=T` 和 `UTC % T == 0`。`GET OUT` 返回的 `NEXT` 仅表示下一次 PPS_OUT 输出
时间，不是本次周期修改选择的目标对齐 UTC，不能用 `NEXT` 替代上述事件校验。

双网关使用相同 GPS UTC 基准和相同周期 `T` 时，应分别满足：

```text
U1 % T == 0
U2 % T == 0
```

`U1` 与 `U2` 可以相差 `T` 的整数倍，例如两台设备因配置命令到达时间不同而在
不同周期完成切换；这仍表示两者落在同一个 UTC 周期相位网格。软件验证必须记录
两台设备各自的 `CPLD_ALIGNED` 事件、目标周期和完整健康状态。该整除关系只证明
设备内部按同一 UTC 网格对齐，不能替代示波器对两路实际 PPS_OUT 或射频时隙边沿
相位差的测量。

如果 60 秒内没有观察到对齐完成，或者状态没有同时满足 `RUNNING`、`PERIOD=T`、
`PENDING=0` 和 `ALIGN=1`，则按周期配置/对齐失败处理并采集诊断。NS 参数再次修改并产生不同周期时，
必须重新执行 `OUT ON → SET PERIOD`，重新等待和校验新的 `CPLD_ALIGNED` 事件，
不得沿用上一次周期的对齐结果。

### 2.5 网关 GPS/PPS 状态机

默认策略参数：模块探测 2 次、单次命令超时 1 秒、搜星超时 300 秒、状态轮询
间隔 10 秒、PPS 对齐超时 60 秒、连续判定门限 3 次。

```text
                              网关启动
                                 │
                       最多两次 GET VERSION
                                 │
                 ┌───────────────┴───────────────┐
                 │                               │
              两次失败                        任意成功
                 │                               │
          ABSENT（无模块）                SEARCHING（等待信号）
                 │                               │
          直接按本地同步启动              每 10 秒 GET STATUS
                 │                               │
                 │                 ┌─────────────┴─────────────┐
                 │                 │                           │
                 │         300 秒内基础状态就绪             300 秒超时
                 │                 │                           │
                 │          EXTERNAL_READY              采集五项诊断
                 │                 │                           │
                 │          收到 NS 时隙配置            LOCAL_DEGRADED
                 │                 │                           │
                 │       OUT ON → SET PERIOD             本地同步启动
                 │                 │                           │
                 │          最长等待对齐 60 秒        连续 3 次基础健康
                 │                 │                           │
                 │       ┌─────────┴─────────┐                 │
                 │       │                   │                 │
                 │     对齐成功            配置/对齐失败       │
                 │       │                   │                 │
                 │ EXTERNAL_ACTIVE      LOCAL_DEGRADED         │
                 │       │                                     │
                 │ 每 10 秒完整健康检查                         │
                 │       │                                     │
                 │ 连续 3 次不健康                              │
                 │       │                                     │
                 │    FAULT，诊断并退出 1                 退出 2 请求重拉
                 │                                             │
                 └────────────── 本地同步运行 ─────────────────┘
```

各状态定义：


| 状态              | 进入条件                           | 8710 同步方式                | 运行期处理                                  |
| ----------------- | ---------------------------------- | ---------------------------- | ------------------------------------------- |
| `ABSENT`          | 两次版本查询均失败                 | 本地：`ls_en=0, ls_master=1` | 不再轮询 GPS，不因 GPS 恢复退出             |
| `SEARCHING`       | 模块版本查询成功                   | 8710 尚未启动                | 等待基础状态，最长 300 秒                   |
| `EXTERNAL_READY`  | `GPS=1、PPS=1、FIX=1、RMC=A`       | 尚未最终选择                 | 等待 NS 计算周期并配置 AG32                 |
| `EXTERNAL_ACTIVE` | 周期生效且完整健康                 | 外部：`ls_en=1, ls_master=0` | 连续 3 次完整异常后诊断并退出 1             |
| `LOCAL_DEGRADED`  | 搜星、周期配置或对齐失败           | 本地：`ls_en=0, ls_master=1` | 连续 3 次基础健康后退出 2，请求保护进程重拉 |
| `LOCAL_STATIC`    | 默认配置、扫频或无有效时隙计算周期 | 本地：`ls_en=0, ls_master=1` | 固定本地同步，不执行 GPS 恢复退出           |
| `FAULT`           | 外部同步运行连续 3 次不健康        | 当前运行终止                 | 采集诊断，统一清理并退出 1                  |

基础健康只判断 `GPS/PPS/FIX/RMC`；完整健康还要求周期正确、`RUNNING`、输出开启、
无待生效周期、已对齐且没有 `HOLD/BAD/RESYNC`。UART 查询失败在外部同步状态下
同样计入连续异常；本地降级状态下查询失败只会清零连续恢复计数。

### 2.6 NS 配置与状态机的关系

- `ABSENT` 或 `LOCAL_DEGRADED` 收到 NS 配置后均按本地同步启动。
- 只有 `EXTERNAL_READY/EXTERNAL_ACTIVE` 且时隙周期可换算为整数秒时，才执行
  `OUT ON`、`SET PERIOD <计算周期>` 并尝试外部同步。
- 默认配置和扫频没有可靠的时隙计算器周期，进入 `LOCAL_STATIC`，不会因后来 GPS
  恢复而退出。
- 当前进程不会把已运行的 8710 从本地同步在线切换为外部同步；降级后 GPS 连续恢复
  3 次时返回退出码 `2`，由新进程重新完成初始化和同步源选择。

## 4. 通用准备与检查

1. 记录网关编号、IP、TK8710/RF板版本、GPS模块序列号及天线连接。
2. 用例 3～6 编译正式网关程序，不使用 `TK8710_GPS_TEST_HOOKS`：

   ```bash
   source ~/arm-buildroot-linux-gnueabihf_sdk-buildroot/environment-setup
   ./cmake/build_rk3506.sh tk8710_gw
   sha256sum build_rk3506/tk8710_gw
   ```
3. 将同一二进制上传到所有被测网关的独立文件名，不覆盖生产程序。
4. 检查无残留被测进程占用 SPI、UART、GPIO 或 IPC。
5. 两台网关设定相同 RF 频点、发送增益、寄存器 `0xA064` 和上下行包块数。

9. 如使用示波器，同时连接两台网关对应的可测时隙/BCN触发信号，使用同一触发源和相同探头设置。具体测试点需结合板卡原理图确认。
10. 每个模式开始前清空本轮统计，但不得删除此前原始日志。

### 4.1 用例 1、2 的 GPS API 测试注入设计

用例 1、2 使用独立测试目标，在 `TK8710_GPS_TEST_HOOKS` 条件下提供以下测试场景。名称为方案约定，实际实现时应保持等价语义：


| 测试场景              | `GET VERSION` 模拟结果  | `GET STATUS` 模拟结果                             | 验证目标                                  |
| --------------------- | ----------------------- | ------------------------------------------------- | ----------------------------------------- |
| `NO_MODULE`           | 连续两次返回超时/无模块 | 不调用                                            | 验证网关按无模块路径立即本地启动          |
| `NO_PPS`              | 返回真实成功版本        | 强制`PPS=0`，其余字段保留真实值                   | 验证 300 秒超时后本地降级并保持运行       |
| `NO_PPS_THEN_RECOVER` | 返回真实成功版本        | 降级前强制`PPS=0`；确认进入降级后恢复真实健康状态 | 验证连续 3 次恢复、退出 2、重拉后外部同步 |

建议测试接口：

```c
#ifdef TK8710_GPS_TEST_HOOKS
typedef enum {
    GW_GPS_TEST_PASSTHROUGH = 0,
    GW_GPS_TEST_NO_MODULE,
    GW_GPS_TEST_NO_PPS,
    GW_GPS_TEST_NO_PPS_THEN_RECOVER
} GwGpsTestScenario;

int GwGpsTestSetScenario(GwGpsTestScenario scenario, const char* run_id);
int GwGpsTestClearMarker(const char* run_id);
#endif
```

注入应位于网关 GPS API 适配层：真实 UART 和 GPS/PPS 硬件保持连接。适配层先调用真实 API 并保存原始结果，再生成网关状态机看到的“有效结果”；日志同时打印原始结果和注入后结果。`NO_PPS_THEN_RECOVER` 必须在网关已经记录本地降级后才能切回真实状态，不能按固定墙上时间提前恢复，否则可能绕过超时降级分支。

测试程序可通过仅测试构建存在的参数选择场景，例如 `--gps-test-scenario no-module|no-pps|no-pps-then-recover`。恢复场景还必须传入只含字母、数字、点、下划线或连字符的 `--gps-test-run-id <id>`。测试场景、切换时刻、每次模拟返回和实际硬件状态都必须写入日志。

`NO_PPS_THEN_RECOVER` 必须是跨进程的一次性注入。旧进程确认降级、解除状态改写并在连续 3 次恢复后退出 `2` 前，应将唯一测试运行 ID 标记为“场景已消费”；保护进程使用同一启动命令重新拉起时，测试层检测到该标记后自动使用 `PASSTHROUGH`。标记文件只能存放在本轮测试目录或 `/tmp` 的唯一文件中，测试结束后删除。若新进程再次进入 `NO_PPS`，本轮恢复闭环判为失败。

测试版网关运行示例：

```bash
./tk8710_gw_gps_ns_test --gps-test-scenario no-module
./tk8710_gw_gps_ns_test --gps-test-scenario no-pps
./tk8710_gw_gps_ns_test --gps-test-scenario no-pps-then-recover \
    --gps-test-run-id sim02r-20260907-01
```

`NO_PPS_THEN_RECOVER` 的标记只在连续 3 次真实健康状态确认后、返回退出码 `2` 前
创建；保护进程按原命令重拉时自动透传。每轮测试必须使用新的 run-id，或在确认测试
进程已退出后清理对应 `/tmp/tk8710_gps_test_<run-id>.done` 文件。

- 正式 `tk8710_gw` 不定义 `TK8710_GPS_TEST_HOOKS`，不包含测试枚举、设置接口或命令行参数。

## 11. 异常处理与复测规则

- 任一网关 GPS/PPS 连续 3 次异常并退出时，本轮判为失败；必须保留退出前诊断，不得只重启后重测。
- 出现 `BAD=1`、`HOLD=1`、`RESYNC=1`、周期不一致或 UART 查询失败时，记录发生时间和持续次数。
- `SET PERIOD` 后 60 秒内未捕获 `CPLD_ALIGNED`，或事件中的周期/UTC 不满足预期时，本轮按周期对齐失败处理；保留原始 UART 事件和诊断状态。
- 出现 RF 通道因 ANoise 保护被禁用、ACM校准失败、IRQ停滞或异常复位时，作为独立失败项记录。GPS同步健康不代表RF链路健康。
- NS 在 HAL 启动前发送的下行数据可能返回发送失败，必须将“配置前失败”和“运行期失败”分开统计。
- 某一模式失败后至少重复 3 次；保留全部失败和复测日志，不只保留成功结果。
- 两台网关配置或二进制不一致时，本轮数据无效，修正后重新开始该模式。
- 多速率集合相同但 `rateModes[]` 顺序不同，也属于配置不一致，本轮数据无效。
- 移动测试失败时，先固定终端位置分别验证单网关链路，再恢复双网关同频环境，以区分覆盖不足、射频通道异常和同步冲突。

## 13. 测试结论

用例1、2、3验证了单网关的GPS模块识别、无PPS超时降级、信号恢复及外部同步启动路径；两台GPS网关的同频同步接收、超帧对齐及下行ACK协同工作正常。各项实测结果及验证范围如下。

1.无GPS模块时本地启动


无模块识别及本地启动状态机通过；

2.无PPS超时降级及恢复

无PPS超时降级、恢复检测及人工重启后的外部同步恢复通过；

3.GPS/PPS正常启动及周期ACM校准

周期ACM重复触发、校准、外部同步恢复及校准后继续运行通过，测试期间2个终端一直保持数据收发，未出现丢包现象。

4.重叠覆盖区域的网关停机与恢复

在两网关重叠覆盖区域，其中一台网关信号明显较强。关闭强信号网关后，终端能够与相对弱信号网关保持正常BCN同步，超帧序号连续，广播未丢包。增加网关BCN发送天线随机配置后，再次启动强信号网关，未观察到连续丢包现象，两网关超帧保持对准。恢复过程中仍观察到广播丢包。

5.不同配置下的同步组网表现

用例4、5、6覆盖了不同速率、超帧及上下行载荷配置。分析所有测试丢包，已观察到的丢包因素包括干扰引起的弱信号网关上行接收丢包，以及终端ACK接收丢包。除上述因素外，在本次已测试范围内，未发现两网关同步接收异常、下行ACK协同异常，或终端频繁丢广播等现象。
