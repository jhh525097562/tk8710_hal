# GPS同步软硬件方案说明

版本：V1.0

整理日期：2026-09-29

软件基线：当前 `tk8710_hal_v1.6`，主程序 `src/gateway/tk8710_gw.c`。

## 1. 方案目标与范围

多台网关采用共同GPS时间基准，通过外部可配置脉冲同步启动TK8710，实现同频组网。
软件负责按业务时隙配置设置脉冲周期，校验实际脉冲与帧/超帧的相位关系，并将周期ACM
安排在下一同步脉冲前的末帧S3内，避免校准后长时间等待脉冲造成业务中断。

本文按当前实现说明。UART健康状态、GPIO时间戳和软件帧校验分别反映不同层面的状态，
不能单独代替多网关射频时隙边界的仪器测量。

## 2. 硬件方案

本方案以 GPS 时间为共同基准，由 AG32 GPS 同步控制板生成可配置周期的
PPS_OUT，再由 TK8710 的 GPIO 输入捕获该脉冲。软件通过串口配置 AG32、
读取状态并监测实际到达的 GPIO 上升沿。

硬件方案的目标是将“时间基准”“同步脉冲输出”和“业务时隙启动”明确分层：

- GPS 接收模块提供时间、定位状态和原始 PPS 基准。
- AG32 负责依据 GPS 状态完成对齐，并产生给网关使用的 PPS_OUT。
- TK8710 仅以实际接收到的 PPS_OUT 上升沿作为外部同步锚点。

### 2.1 硬件组成与连接

```text
┌──────────────────────┐
│ GPS 天线 / GNSS 信号 │
└──────────┬───────────┘
           │
           v
┌──────────────────────┐
│ GPS 接收模块          │
│ - UTC / RMC           │
│ - 原始 1 Hz PPS       │
└──────────┬───────────┘
           │ GPS 串口与 PPS_IN
           v
┌─────────────────────────────────────────────┐
│ AG32 GPS 同步控制板                          │
│  CPU：GPS 解析、UTC 周期选点、串口协议       │
│  CPLD：PPS_IN 捕获、对齐、PPS_OUT 生成       │
└───────┬───────────────────────┬─────────────┘
        │ UART，115200，8N1     │ PPS_OUT，上升沿
        │                       │
        v                       v
┌───────────────────┐   ┌──────────────────────────┐
│ TK8710 UART       │   │ TK8710 GPIO               │
│ /dev/ttyS4        │   │ gpiochip1 line18          │
│ 配置、状态、事件  │   │ 实际同步脉冲监测输入      │
└───────────────────┘   └────────────┬─────────────┘
                                      v
                         ┌──────────────────────────┐
                         │ TK8710 HAL / TRM / ACM   │
                         │ 业务时隙启动与周期校准   │
                         └──────────────────────────┘
```

AG32 复位线接入 TK8710 `gpiochip1` line19，低有效。该接口保留给维护和
人工恢复使用；当前网关异常保护流程不自动拉低该复位线。

| 接口 | 方向 | 作用 | 备注 |
| --- | --- | --- | --- |
| GPS 天线 | 外部 -> GPS 接收模块 | 接收卫星信号 | 天线、馈线和接收环境决定 GPS 可用性。 |
| GPS 串口 / PPS_IN | GPS 接收模块 -> AG32 | 提供 RMC UTC 与原始 PPS 基准 | AG32 使用有效 GPS 状态完成输出对齐。 |
| UART | TK8710 <-> AG32 | 周期配置、状态查询、主动事件 | `/dev/ttyS4`，115200，8N1。 |
| PPS_OUT | AG32 -> TK8710 | 向网关提供可配置周期同步脉冲 | 接入 `gpiochip1` line18，以实际上升沿为准。 |
| RESET | TK8710 -> AG32 | AG32 硬件复位 | `gpiochip1` line19，低有效。 |

PPS_OUT 是提供给 TK8710 的可配置周期脉冲，不等同于 GPS 接收模块的原始
1 Hz PPS。PPS_OUT 的周期由上层配置决定，TK8710 不应把 line18 固定解释为
1 秒脉冲。

### 2.2 同步脉冲分配、电气接口与时序

同步关系如下。UTC 与对齐由 AG32 完成；TK8710 不根据串口数据推测脉冲到达
时间，而是等待 GPIO18 上实际出现的上升沿。

```text
GPS PPS_IN        ────────┐       ┌───────┐       ┌───────┐
                           └───────┘       └───────┘
GPS RMC/UTC       ---- UTC、定位与有效状态 -----> AG32 CPU
                                                   │
AG32 对齐控制                                      │ 选择满足 UTC % 周期 == 0 的秒点
                                                   v
AG32 PPS_OUT      ────────────────────────┐       ┌────────┐
                                           └───────┘        └────
                                                   │
TK8710 GPIO18     ────────────────────────┐       ┌────────┐
                                           └───────┘        └────
                                                   │ 上升沿捕获
                                                   v
TK8710 S0/时隙     等待外部脉冲 -> 建立锚点 -> 启动业务帧 -> 在周期末帧安排 ACM
```

时序约定：

1. TK8710 通过 UART 向 AG32 发送 `OUT ON` 和 `SET PERIOD <period>`。
2. AG32 在 GPS 时间有效时选择目标 UTC；目标秒点满足 `UTC % period == 0`。
3. AG32 完成对齐后，开始输出对应周期的 PPS_OUT，并通过 UART 上报对齐完成事件。
4. TK8710 捕获 GPIO18 的实际上升沿，将第一个合格边沿关联为 S0 锚点；后续帧和
   ACM 窗口均以该锚点为依据。

电气接口应遵守以下原则：

- PPS_OUT 与 GPIO18 必须共地，且电平、驱动能力、边沿质量满足双方硬件规格。
- PPS_OUT 应为单一、清晰的上升沿触发信号；毛刺、反射和重复边沿会影响同步判断。
- UART 与 PPS_OUT 是独立通道：UART 用于控制和状态，GPIO18 上升沿用于实际同步。
- 具体电平标准、接口保护、线缆长度和终端匹配由硬件设计文件确认，本方案不以软件
  假设替代电气设计结论。

### 2.3 测试点与硬件验证结果

建议在样机和量产验证中保留以下观测点：

```text
GPS 原始 PPS ── TP1 ──> AG32 PPS_IN
AG32 PPS_OUT ── TP2 ──> TK8710 GPIO18
AG32 UART    ── TP3 <──> TK8710 UART
AG32 RESET   ── TP4 <──  TK8710 GPIO19
```

| 测试点 | 验证内容 | 合格判定 |
| --- | --- | --- |
| TP1：GPS 原始 PPS | GPS 基准是否稳定到达 AG32 | GPS 就绪后具有连续、稳定的 PPS 上升沿。 |
| TP2：AG32 PPS_OUT | 输出周期、脉宽、重复边沿和对齐后的稳定性 | 与配置周期一致，无额外脉冲、漏脉冲或异常秒级跳变。 |
| TP2 与 GPIO18 | 输出端至 TK8710 输入端的连通性和边沿可见性 | 示波器可见 TP2 边沿，TK8710 同时记录 GPIO18 上升沿。 |
| TP3：UART | 命令、应答和主动事件链路 | 可完成状态查询、周期配置，并收到对齐完成事件。 |
| TP4：RESET | 复位极性和恢复行为 | 人工拉低后 AG32 可按设计重新启动；正常运行不应误触发。 |

多网关同步验收应使用同一测量基准对各网关的实际 PPS_OUT 或射频时隙边界进行
仪器测量。GPIO18 监测和 UART 状态仅证明本机链路与软件状态正常，不能单独替代
跨网关射频相位精度的最终结论。

## 4. GPS配置与启动流程

### 4.1 NS策略

当前程序先启动IPC、获取NS配置，再决定是否启动GPS功能。

| `gps_enable` | 当前网关行为 |
| --- | --- |
| 0 | 选择本地同步，不要求GPS就绪 |
| 1 | 必须探测到模块、GPS基础信号就绪且脉冲配置对齐成功，才能启动业务 |
| 非0/1或不兼容配置长度 | 拒绝配置 |

当前IPC要求完整 `NsConfigDown_t`，包含末尾的 `gps_enable`；已不采用旧版本临时
强制开启或兼容缺字段长度的策略。未取得明确NS配置时拒绝默认业务启动。

GPS管理模块仍包含 `ABSENT`、`LOCAL_DEGRADED` 和恢复退出码2等历史状态；但当前
网关在 `gps_enable=1` 时要求启动结果为 `EXTERNAL_READY`，否则报错退出。
模块内部返回降级状态，不代表当前主程序允许降级运行。

### 4.2 外部同步启动顺序

```text
获取并校验NS配置（gps_enable=1）
  → 停止旧GPIO监测、关闭旧GPS上下文
  → GET VERSION探测，等待GPS基础就绪
  → HAL初始化（包括启动ACM）、时隙计算
  → OUT ON → SET PERIOD <计算周期>
  → 等待周期生效和完整健康
  → 应用外部同步时隙配置
  → 配置TRM的PPS循环计数、申请GPIO18监听
  → TK8710HalStart，硬件等待外部同步脉冲
  → 首个实际S0关联GPIO边沿并建立相位锚点
  → 运行期UART/GPIO/帧状态监控
```

探测最多2次，每次命令超时1秒；搜星最长300秒，每10秒查询一次。
基础就绪要求 `GPS=1、PPS=1、FIX=1、RMC=A`。
脉冲配置后最长等待60秒，完整健康要求：

```text
STATE=RUNNING、PERIOD=期望周期、OUT=1、PENDING=0
GPS=1、PPS=1、FIX=1、RMC=A
ALIGN=1、HOLD=0、BAD=0、RESYNC=0
```

UART按行拆帧，命令响应可穿插 `EVENT`，主动事件不当作命令应答；未知字段可忽略。
`OK PERIOD`表示命令受理，主程序继续轮询完整状态确认生效，不仅凭命令回复启动。

### 4.3 同步模式寄存器

| 模式 | `local_sync` | `ls_en` | `ls_master` |
| --- | ---: | ---: | ---: |
| 本地同步 | 1 | 0 | 1 |
| 外部GPS/PPS同步 | 0 | 1 | 0 |

普通启动和ACM快速启动使用相同同步配置辅助逻辑，避免校准重启覆盖同步源。
NS参数更新后重新执行配置流程，新周期对齐后重新建立GPIO及TRM锚点，不沿用旧周期计数。

### 4.4 周期计算与UTC对齐

令 `R` 为速率数量，`F` 为一个完整速率循环的时长，`N` 为循环数，`S` 为业务`tdd_num`：

```text
F = 各速率帧的(S0 + S1 + S2 + S3)之和
PPS周期 T = F × N / 1000000 秒
N % S == 0
```

对应计算器输出 `framePeriod=F`、`frameCount=N`。单速率时F即一个帧周期；多速率时
F是完整速率循环，不等于其中某一个速率帧长。使用64位乘法并校验整数秒和取值范围。
监测模块额外检查各速率帧长之和、S0长度及最短帧长等参数。

根据AG32协议，对齐目标UTC秒点U应满足 `U % T == 0`。相同周期的网关可在相差T整数倍
的UTC秒点完成启动，属于同一周期相位网格。当前主程序通过状态轮询确认RUNNING/ALIGN，
GPIO进一步校验本机实际脉冲；并未逐条解析 `CPLD_ALIGNED` 的UTC值来自动证明跨网关相位。

## 5. 脉冲与业务超帧、虚拟超帧的对齐

### 5.1 三种计数的含义

| 名称 | 用途 | 更新规则 |
| --- | --- | --- |
| 累计业务帧号 `g_trmCurrentFrame` | 队列年龄、波束释放、业务超帧取模 | 正常S3结束递增；ACM接管S3时补一次虚拟S3 |
| 业务超帧位置 | 广播和业务帧位置 | `累计业务帧号 % S + 1`，范围1～S |
| PPS周期位置 `g_acmPpsClock` | 识别下一个脉冲前的末帧 | 每个实际S0记录速率，回到rate0时增加循环索引，范围0～N-1 |

本文称无业务超帧时的内部PPS周期组织为“虚拟超帧”：`S=1`时业务位置始终为1，
但仍维护PPS周期内N轮速率循环，用于同步检查和ACM调度。这不是新增的空口超帧字段。
“虚拟S3”则是另一概念：校准替代正常S3后，软件补一次帧结束，防止业务帧计数漏加。

### 5.2 GPIO锚点与逐帧校验

独立GPIO线程保存内核上升沿时间戳；S0回调记录软件单调时间、循环索引、速率索引及
业务超帧位置。GPIO线程先排空边沿队列，再处理延后20ms的帧观察，缓解线程处理顺序差异。
首次帧必须为cycle0/rate0，估计帧起点与实际脉冲匹配后才建立锚点。

```text
估计帧起点 = S0回调单调时间 − 当前速率S0长度
预期周期相位 = cycle_index × F + 前面各速率帧长之和
预期业务超帧位置 = (cycle_index × R + rate_index) % S + 1
```

检查内容包括脉冲间隔、周期内帧相位、相邻S0间隔、速率轮转和业务超帧位置。
累计业务帧号不由GPIO线程清零或倒退；整帧错位时退出重新启动，不仅修改软件数字。
没有超帧时同样执行PPS周期位置检查。

| 示例 | 关系 | ACM窗口 |
| --- | --- | --- |
| 单速率，S=1，F=280ms，N=25 | 每7秒脉冲包含25帧，业务位置一直为1 | 第25帧S3 |
| 单速率，S=10，F=700ms，N=10 | 每7秒脉冲对应一个业务超帧 | 第10帧S3 |
| 单速率，S=20，N=40 | 每脉冲对应两个业务超帧 | 第40帧S3，而非第20帧 |
| 四速率，S=1，F=3秒，N=1 | 每脉冲对应一轮四速率帧 | 第4个速率帧S3 |

多速率每周期共有 `N × R` 个业务帧，故对应 `(N × R)/S` 个业务超帧。

### 5.3 时间基准

GPIO事件、S0关联和外部ACM脉冲期限使用 `CLOCK_MONOTONIC`。
libgpiod 1.x监测编译单元使用 `_FILE_OFFSET_BITS=64`、`_TIME_BITS=64`，与SDK事件结构匹配。
不能直接将GPIO单调时间与 `gettimeofday()` 日期时间相减。
S0为软件回调时间，包含中断处理和调度延迟；它不是8710硬件边沿采样时间。

## 6. GPS异常保护

### 6.1 保护规则

| 异常 | 当前处理 |
| --- | --- |
| 开启GPS但模块探测/搜星失败 | 拒绝业务启动，主程序报错退出 |
| OUT ON、SET PERIOD或对齐失败 | 保存诊断并拒绝外部同步业务启动 |
| UART运行状态连续3次异常/查询失败 | 采集诊断并请求致命退出 |
| GPIO连续丢失1～4个预期周期 | 暂停新的ACM，保留pending请求；尚在运行的业务继续 |
| GPIO恢复 | 清零丢失计数；与后续帧相位匹配后恢复ACM资格 |
| GPIO连续丢失5个预期周期 | 锁存致命状态，主循环退出，由保护进程重拉 |
| GPIO读取失败、事件洪泛、帧队列溢出 | 请求退出，避免继续使用不可靠同步状态 |
| 相位严重偏移/业务超帧位置错误/帧漏计 | 请求退出重新同步 |

运行期UART默认每10秒轮询。其三次策略与GPIO五周期策略并不简单叠加：仅在GPIO已确认
短期丢脉冲、UART报告PPS=0且GPS在线、FIX有效、RMC=A、周期正确、无BAD/ERROR时，
暂交由GPIO五周期策略处理。其他GPS定位、UART或设备错误仍按原三次异常策略处理。
因此“五次才退出”仅针对该脉冲丢失分支，不屏蔽其他独立故障。

诊断命令依次包括 `GET PPS`、`GET OUT`、`GET SYNC`、`GET GPS`、`GET RMC DIAG`。
公共API提供复位能力，但当前主程序保护采用退出/外部守护重拉，不自动复位AG32。

### 6.2 偏差阈值与日志

| 条件 | 处理 |
| --- | --- |
| 帧相位偏差>1ms但未达致命阈值 | `PPS frame check ... result=1`，WARN |
| 相位容差 | `min(5ms, 最短速率帧长/4)`，超过后不允许新ACM |
| 相位或相邻帧间隔偏差≥最短帧长/2 | 判定关联失败，ERROR并退出 |
| 业务超帧位置不符合预期 | ERROR并退出 |
| 额外边沿间隔<脉冲周期/2 | 作为毛刺忽略，不重置丢失计数 |

丢失次数按“距离最近有效边沿的预期周期数”计算，并留出相位容差；首次无边沿时从
监听启动时刻计算。线程独立于8710中断，因此硬件等待脉冲、没有S0时也能超时退出。
保留32个边沿、256条S0观察。正常GPIO/周期首帧日志为TRM INFO，异常为WARN/ERROR。

### 6.3 状态发布与退出清理

每次GPS状态查询成功后查询 `GET POS`，原子更新 `/userdata/GPS/GPSinfo.txt`：

```text
lon=114.005377
lat=30.004928
status=5
```

经纬度为十进制度、6位小数。status是当前进程连续基础健康且位置有效的次数，异常归零，
恢复从1递增；它不等同于GPIO同步健康或完整PPS健康。位置不可用时写零坐标。
同时RF检测结果写入 `/userdata/RFStatus/RFstatus.txt`，与GPS故障分别管理。

统一退出停止相关线程和IPC、关闭UART、清理HAL，最后清空GPS/RFStatus目录中的状态
及临时文件，保留目录；不发送OUT OFF。退出码通常0为正常，1为故障，历史降级恢复
分支使用2请求重拉。SIGKILL或断电不能执行正常清理，读取方还应考虑文件新鲜度。

## 7. 周期ACM校准

### 7.1 周期请求

当前 `TRM_ACM_PERIODIC_INTERVAL_MINUTES=60`。TRM初始化时记录单调时间，之后在S2
回调检查是否达到间隔；请求成功后更新计时基准。请求pending/running期间不重复提交。
日志的 `elapsed_us` 应不小于 `3600000000`，实际执行还需等待合适的PPS末帧窗口。

周期计时已修复为 `TK8710GetMonotonicTimeUs()`，避免系统校时影响；公共日期微秒函数
也已修复乘法前的64位扩展，消除原“60分钟后又隔约11分半请求”的32位溢出问题。
校准因子文件继续保存日历时间，因此文件相邻时间不严格代表请求间隔。

### 7.2 执行资格与窗口

外部同步下，只有同时满足下列条件才执行：

1. 存在pending请求，未在校准、未请求退出且非扫频状态。
2. PPS循环计数达到末轮，当前为末速率帧的S2结束。
3. GPIO已建立锚点、当前帧相位有效，无丢失或致命故障。
4. 距下一预测脉冲的时间足够完成校准与准备。

```text
预算 = 28000us × calibCount + guardUs + restartAdvanceUs
默认周期请求：calibCount=1、snrThreshold=24
guardUs=1000、restartAdvanceUs=400
```

窗口不足就保留请求、继续业务、等待后续周期；若每周期窗口都不足，需调整时隙或
校准参数。无GPIO监测的其他调用者仍可能使用已有软件末帧路径，不能视为具备实际脉冲校验。
本地同步保留业务超帧末帧S3和软件精确重启时间等待策略。

### 7.3 校准与恢复顺序

```text
末轮末速率S2结束
  → ACM校准 → 恢复时隙配置
  → 切换到下一轮首速率
  → FastStartPrepare
  → 核对GPIO单调期限和安全裕量
  → 标记校准重启等待 → FastStartTrigger
  → 补一次虚拟S3（仅业务计数，PPS计数等待实际S0推进）
  → 实际脉冲到达 → 硬件运行 → 首S0校验cycle0/rate0及业务超帧位置
```

外部同步无需软件卡住精确帧末时间，提前准备后由硬件等待脉冲。但准备或触发超出
已预测期限时直接请求退出，不假装只丢失一帧后继续。校准负返回或恢复失败也按故障处理。
无有效校准结果可重试；连续失败默认达到20次时请求退出。

无法在校准开始前预知下一脉冲将丢失。若校准完成后脉冲丢失，硬件维持等待状态；
恢复后允许实际脉冲重新启动，首S0必须匹配恢复边沿，连续5周期未恢复仍退出。
普通运行时的异常长帧间隔没有这个豁免。重启标记带时间戳，避免旧排队观察误消费。

## 8. 验证情况与已知限制

| 范围 | 已有证据与边界 |
| --- | --- |
| 单速率S=1 | `.239` 7秒脉冲、5帧周期，1分钟测试版多次在5/5帧校准并恢复 |
| 单速率S=10 | `.239` 700ms单帧、7秒脉冲，10/10帧校准及恢复通过；当时发现周期计时溢出 |
| 四速率S=1 | `.239` 模式6/7/8/9，3秒循环，末速率4/4校准，恢复首速率1/4校验通过 |
| 计时修复 | 边界、模拟6小时及ACM/PPS回归测试通过；修复后超过两小时板测未记录 |
| 丢脉冲保护 | 模型测试覆盖丢失1～4次恢复及5次退出；人为阻断GPIO板测未记录 |
| 多网关组网 | 见独立验证文档；不能以单网关GPIO相位正常代替射频物理同步结论 |

S0时间来自软件回调，长时间调度阻塞可能产生保守退出，容差需结合板端延迟分布确认。
libgpiod v1接口未提供可用的事件溢出序号，脉冲监测面向低频同步信号。
多速率ACM当前仍存在将末速率S3与刷新后的首速率S3比较的告警口径问题，已有板测中
恢复相位通过，但不能仅以此告警判断配置错误。部分板测有缺失TxDC或RF7异常，需独立处理。
