# GPIO同步脉冲与超帧、ACM校验

## 信号与时间基准

输入为AG32输出给8710的可配置同步脉冲：核心板91脚、GPIO1_C2、
`/dev/gpiochip1` line18，上升沿；不是GPS原始1Hz PPS。line19为复位信号，不操作。
外部同步网关独占申请line18，申请失败拒绝启动业务；停止、NS重新配置和HAL清理时释放。
不能同时运行pps_counter或其他申请该引脚的工具。

`trm_pps_monitor.c`使用libgpiod 1.x及独立线程，编译单元显式启用
`_FILE_OFFSET_BITS=64`、`_TIME_BITS=64`，匹配SDK事件结构。对外只传固定宽度微秒数，
不暴露timespec ABI。GPIO内核事件与S0观察、ACM期限判断均使用CLOCK_MONOTONIC，
不与gettimeofday绝对时间相减。原ACM日志可将剩余时长换算为旧时间基准显示。

## 配置、帧单位和首次锚定

网关在新PPS配置对齐完成后、TK8710HalStart之前启动监听，传入计算器的
framePeriod、frameCount、每速率四个slot的总长度和BCN slot长度，以及业务tdd_num。
framePeriod是完整速率循环时长，frameCount是一个脉冲周期中的循环数；要求
`frameCount % tdd_num == 0`，各速率帧长之和等于framePeriod，脉冲周期为整数秒。

首次实际S0必须是cycle0/rate0，减去该速率S0长度后与GPIO边沿匹配，建立共同锚点。
之后周期相位应等于`cycle_index * framePeriod + 前面各速率帧长之和`。
业务超帧位置应等于`(cycle_index * rateCount + rateIndex) % tdd_num + 1`。
累计业务帧号不回退、不在GPIO线程清零，避免影响发送队列年龄与波束释放。
每个S0都检查相邻帧间隔，漏掉整轮周期也不能靠模计数绕过检查。

无超帧时tdd_num=1，但仍按完整PPS周期数帧，例如7秒/280ms=25帧，
ACM在cycle25/25执行；多速率在最后一轮的最后一个速率帧执行。

## 事件顺序、偏差和丢失策略

GPIO线程先排空边沿队列，再处理延后20ms的S0观察。保留32个边沿及256条帧观察，
按事件时间关联，避免GPIO与8710线程先后顺序不同导致边界错配。
观察溢出、GPIO读取错误、事件洪泛均明确请求退出，不继续使用不可靠计数。

容差为min(5ms, 最短速率帧长/4)，配置帧长不得小于4ms；1ms以上的帧相位偏差打印记录。
达到最短帧长一半的相位/帧间隔偏差，或业务超帧位置不符，认定同步关联失败并请求退出。
小于整帧判据的偏差保留记录；超过ACM容差时暂停ACM，待实际边沿和帧重新匹配后恢复。
小于半个脉冲周期的额外边沿作为毛刺忽略，不清零丢失计数。

每个预期周期超时（加上述容差）增加一次丢失计数：

- 丢失1～4次：暂停新的ACM，保留pending请求，正常业务仍继续；
- 脉冲恢复：有效边沿清零丢失计数，与帧相位校验成功后允许后续ACM；
- 连续丢失5次：锁存致命状态，由网关主循环返回1并交由保护进程重拉。

独立线程在没有8710帧中断时仍计算脉冲超时。收到脉冲不等于立即放行ACM，
必须有该边沿对应的帧观察。原UART策略中，仅“GPIO已经确认丢脉冲且UART的PPS=0、
GPS定位仍正常”的情形交给GPIO五周期策略；GPS定位异常、UART通信异常、BAD/ERROR等
独立故障仍按既有策略退出。

## ACM与恢复

ACM须同时满足原周期末帧条件和实际GPIO预测的下一脉冲期限，时间预算充足才执行。
丢脉冲期间只跳过窗口，不清除校准请求。校准完成后首速率准备完成再触发等待外部脉冲。
无法在校准开始前预知下一个脉冲是否会丢失：若此时丢失，硬件继续等待，允许恢复后的
实际边沿启动；首S0必须在恢复脉冲的cycle0/rate0，业务只补一次虚拟S3。
没有校准重启标记的异常长帧间隔不获豁免。重启标记带时间戳，旧排队S0不会误消费标记。
校准准备/触发错过已预测的期限仍明确退出，不伪装为正常恢复。

## 验证范围

`test_trm_pps_monitor.c`为确定性时间模型测试，覆盖首次锚定、配置校验、多速率与业务超帧、
帧漏计、毛刺、轻微偏差、线程处理顺序、四次丢失恢复、五次丢失退出、ACM等待恢复及新配置
拒绝旧事件。原ACM调度测试继续保留。

板端需分别验证7秒/280ms无超帧、frameCount大于业务tdd_num、多速率和NS重新配置；
人为阻断1～4个及5个脉冲周期，核对pending保留、恢复与退出日志，并观察终端广播/ACK。
S0是软件回调时间而非内核硬件时间戳，系统长时间调度阻塞可能导致保守退出；20ms事件
等待和5ms容差需以板端实际延迟分布验证。本次不把模型测试或交叉编译当作脉冲实测通过。
